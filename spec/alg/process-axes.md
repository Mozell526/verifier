# 第一章：协议标准

## 1. 我们在评什么

三个角色：

- **被测系统**：业务系统，一次运行留下一条业务 trace；
- **消费者**：业务系统开发者（决定修哪里，分清功能问题与算法问题）、评测方自己（解释主轴为什么没办成）；
- **我们**：过程六轴。

六轴对被测系统的六项过程能力各下一个结论。每个 case 每个轴产出两样东西：

```text
verdict   这项能力本次如何（枚举，可跨样本汇总）
reason    归到这个轴的问题，每条带 trace 依据；以及本轴的组成（几项做到、几项没做到…）
```

两样东西分别服务需求里的两类用途：verdict 服务"看整体哪项能力好哪项差"（需求 §2.1）；问题服务"看单个 case 出了什么"和"把问题聚类"（需求 §2.2、§2.3）。**一个值不同时表达两件事。**

## 2. 判定单位：子能力 × 一次行使

每个轴是一项能力，拆成若干子能力。一次运行里，每个子能力被行使零到多次。**判定单位 = 子能力 × 这个子能力的一次行使**。例：第 2 次模型调用 × 输出忠实；子问题 Q1 的取数 × 数据存在。

### 2.1 子能力从哪来

每个轴对应一类部件，部件有固定的"输入 → 输出"。子能力 = 输出里必须保住或产出的每一个方面。这是生成规则，不是手列；§8 按它逐轴推一遍。

| 轴 | 部件 | 输入 → 输出 |
|---|---|---|
| 意图理解 | 表达 | 用户原文、被指代的历史 → 系统内部表达 |
| 规划路由 | 编排 | 任务、当时状态、规则 → 路径、调用序列、重试、收尾 |
| 工具执行 | 执行 | 已发出的调用参数 → 返回 |
| 知识数据 | 数据源 | 已正确执行的查询 → 数据是否存在、是否匹配 |
| 模型能力 | 模型 | 一次调用的实际输入 → 该次输出 |
| 上下文管理 | 传递 | 一处产出 → 下一处输入（含组装、缓存、历史、交付） |

一个 trace 事件可以承载多个轴的单位（模型一次调用的输出既是模型轴的单位，其中的工具参数又是意图轴的单位）。单位属于哪个轴，看它查的是哪一段输入 → 输出。

### 2.2 行使从哪来（需求：两条来源都要）

- **从运行里数**：trace 里发生过的步骤、调用、模型调用、传递，每一次都是一次行使。分析轴负责把它们列全并标出可疑点，不下结论。
- **从需求倒推**：需求轴产出的需求清单 E（用户和下游要什么，`spec/alg/expectations.md`）逐条回答四个问题，决定哪些行使**应该发生**：
  1. 要满足它，需不需要外部数据（依据需求本身、时效和任务性质，不能由"有工具"推出）；
  2. 系统有什么办法拿到（读设计原文中的工具说明，只证明候选办法）；
  3. 当时是否仍必须行动：**已满足**（有效数据、缓存、等价路径，附证据，不展开单位）／**必须做**（成为应发生单位）／**说不清**（保留为单位，落缺证）；
  4. 实际做了没有。

  是否"应发生"由第 3 问决定，与实际有没有发生无关。应发生而 trace 里没有的，也是一个单位，判法见 §3。完整定义见 `spec/alg/expectations.md` §6.2。

没有第二条来源，"该做没做"永远看不见。

## 3. 一个单位怎么判

### 3.1 唯一的对照

```text
这次行使实际产出了什么   vs   在它实际拿到的输入下，本应产出什么
```

"本应"相对于**实际拿到的输入**。理由：verdict 评的是能力，一次行使只有在输入有效时才说明这项能力；输入已经坏了，这次说明的是上游。这条对照是全协议唯一的归属规则，六轴共用，各轴义务文本里不再各写归属分句。

### 3.2 单位的取值

对照要成立，需要四个前提：这次行使发生了、有判准、输入输出看得见、输入有效。每缺一个，对照就以一种不同的方式做不下去，后续动作各不相同。前提齐了，对照只有两个结果。所以单位的取值是：

判定者对"做到"只交支撑它的记录编号，看不全时逐条写范围限制（例如原始请求被脱敏），不写说明；其余取值写清看到了什么。"做到"本身只进轴的组成，四个使用角度都不读它的说明（需求 §2）。

| 取值 | 什么时候 | 后续动作 |
|---|---|---|
| 做到 | 前提齐、产出符合 | 无 |
| 没做到 | 前提齐、产出不符 | 产生一条问题，归本轴 |
| 输入无效 | 行使发生了或应发生，但它依赖的输入不存在或已错；**必须指向一条已记录的上游问题** | 不产生本轴问题；指向上游 |
| 缺证 | 产出看不见，或产出不符但输入有效性看不见 | 补证。后一种同时产生一条问题，归因写"未定位" |
| 缺判准 | 说不出本应产出什么（无出处） | 列入判准清单交用户；不进 verdict 汇总 |
| 未发生 | 这项子能力本次不需要（有正面记录） | 无 |

"输入无效"和"未发生"的区别：前者是**应该**有有效行使而没有，后者是本来就不需要。应发生而 trace 里没有的单位（§2.2 第二条），**不预设责任方**：按证据定位它为什么没发生（规划漏安排、需求在上游漏传、意图没识别出来等）。定位到具体、有证据的上游问题，依赖它的单位落"输入无效"并指向它；定位不了则落"缺证"，问题记录写"归因未定位"并列候选轴。应发生单位不能落"未发生"。

### 3.3 三条堵口子的规则

过去发生过"问题归了某轴，别的轴就当没事"的情况。单位级判定本身不会这样：每个轴的每个单位各判各的，没有"已经归给别人所以跳过"这一步。再加三条：

1. **"输入无效"必须指向一条具体、有证据的上游问题记录。** 指不出来就不能用，只能落缺证。"归别的轴"不再是一句话，是一个必须存在的引用。
2. **"输入无效"只作用于依赖那份输入的子能力。** 模型输入丢了提示，"输出忠实"的输入不完整；但模型同时编了一个输入里没有的数字，"不编造"不依赖那份提示，照判。
3. **同一事件允许多轴各记问题，不去重。** 工具把别的保单标成目标返回（工具轴没做到），目标保单在库里也确实没有（知识轴没做到）：两条问题。

剩余缺口说清楚：输入无效时，我们不知道这个部件在正常输入下会不会做对。协议不假装知道，记成"未检验"（§5）。

### 3.4 判准从哪来

§3.1 的"本应产出"需要出处。一个单位的判准有三种：

| 判准 | 例子 | 引用 |
|---|---|---|
| 通用义务 | "不编造"：本轴子能力的定义，对所有 case 成立（§8） | 义务编号 |
| 需求 | 需求清单 E 中适用的条目（应发生单位挂它展开自的那条；终答相关单位挂对接到的那几条） | E 的编号 |
| 设计规则原文 | 业务模型收到的系统提示词中"输出 JSON：answer_draft 必须是首字段"；某个工具的说明 | 原文位置＋原样摘录；条件、例外在别处时一并关联多处原文 |

设计规则**不进需求清单**，是判定时的证据。能用在哪一步，按轴区分：

| 轴 | 能用的设计规则 |
|---|---|
| 模型能力 | 只能用该次调用**实际收到的**规则；没收到的规则不能拿来判它违约 |
| 上下文传递 | 比较**本该送到的**与**实际送到的**；本该送到而实际没有，就是漏传 |
| 工具执行、规划 | 已确认适用于**这一次执行**的规则（来源、角色、版本对得上） |

设计原文由程序按步交付、每段只交付一次（优先该步实际收到的那份），判定者引用时写案卷编号＋原样摘录，不做逐块标注。只有采集时定义、没有实际收到的那份时，只能作参考，不能单独认定违约或漏传；原文中的数据、示例不是规则；摘录原样完整（不截掉范围词、条件、否定）。判为做到时只交原文摘录和支撑记录编号；程序判准已能判做到的单位不另引规则。判定者挑漏规则不靠它自我声明来防，靠独立审阅与对照样本发现。问题记录的"预期"由程序从引用的判准原样组成，保留条件。完整定义见 `spec/alg/expectations.md` §6.3–§6.5。

source=trace/case 的义务模板，既没有适用的需求、也没有可引用的设计规则时，落"缺判准"。

## 4. 问题记录

问题 = "没做到"的单位，或"产出不符但输入有效性看不见"的单位。字段由两类消费者决定：

```text
轴 / 子能力 / 行使实例（trace 两端引用）
预期（本应产出什么，带出处） / 实际（产出了什么，带引用）
归因：本轴 ｜ 未定位{轴, 轴}
影响：对最终交付有 / 无 / 不明
来源：运行召回 ｜ 期望倒推
```

问题是聚类的成员单位（需求 §2.3），不是整段轴级 reason。

## 5. 轴 verdict

verdict 回答"这项能力本次如何"。对本轴所有单位（缺判准的除外）汇总，取第一个成立的：

| verdict | 条件 | 含义 | 后续动作 |
|---|---|---|---|
| problematic | 有任一"没做到" | 有归到本轴的问题 | 修本轴 |
| not_evaluable | 否则，有任一"缺证" | 行使了，但看不清 | 补证 |
| sound | 否则，有任一"做到" | 已核实范围内没问题 | 无 |
| untested | 否则，有任一"输入无效" | 本应行使，但没有一次输入有效的行使；本次对这项能力没有结论 | 修上游；记评测覆盖缺口 |
| not_applicable | 否则（全部"未发生"） | 本次不需要这项能力 | 无 |

五个值对应五种不同的后续动作，这是它们存在的理由。untested 是新增值：它不是"没问题"，是"没测到"，在六个轴上都成立（历史没注入则指代解析未检验；没发查询则数据能力未检验；输入被弄坏则模型未检验；预算拦截则执行未检验）。

**verdict 永远和组成一起出，组成是输出的一部分：** 几项做到、几项没做到、几项缺证、几项输入无效（各指向哪条问题）、几项未发生、几项缺判准。这是 P4（problematic 盖掉缺证项）和 P5（sound 被读成全部核实）的解法：不加枚举，不丢组成。

归因未定位（P2）的汇总后果：两个轴都落 not_evaluable，问题记录归因写"未定位{工具, 知识}"。一个问题不会同时抬高两个轴的缺陷率。相应地，不变量从"结果坏 ⇒ 至少一轴 problematic"改为"结果坏 ⇒ 问题列表里至少一条记录"。

## 6. 评测器自身的失败

模型没给出合法输出、超时、预算耗尽，是评测运行的 error，记在运行状态上，**不进单位取值，不写成缺证**（需求 P6、§2.4）。

## 7. 主轴

主轴（扩展轴 fulfilled）最终基于六轴综合判断，方向已定（需求 §4），规则与启用时机另行约定。本文不定义。

## 8. 子能力逐轴推导

按 §2.1 规则，从各部件的输入 → 输出推子能力，对照现有义务：保留的注明对应，删除的说明原因。

**意图理解**（用户原文 → 内部表达）。原文里有五样东西必须被表达保住：对象与字段、子问题、约束、指代、不确定性。
→ 对象与字段一致、子问题均识别、约束保留、指代解析、歧义识别。现有五条全部对应，保留。

**规划路由**（任务 + 状态 + 规则 → 决策）。输出是一组决策，每种决策都要与输入一致：选路径、给每个子问题安排工作、分支、失败后的动作、重复调用、工具返回后的整合、收尾、系统自身策略。
→ 路径选择、工作覆盖、分支按声明条件、失败分支有产出、重复调用有依据、工具返回后的整合与交付、结束时机、系统策略。现有八条对应。`decision_matches_rule` 保留为"表外决策"的兜底形式。

**工具执行**（调用参数 → 返回）。返回必须：执行完成、就是请求的对象且完整、在时限内。
→ 调用无执行错误、返回对象与请求一致（含"按请求条件执行，未丢条件"）、耗时在限。
删 `empty_or_rejection_expected`：它的内容是"空结果归工具还是归数据源"的归属判断，由 §3 的对照取代。工具侧原因（解析丢条件、适配层不支持）并入"返回对象与请求一致"；系统策略拒绝使调用未发出，落 untested 指向规划。

**知识数据**（已正确执行的查询 → 数据）。数据必须：存在、匹配。
→ 数据存在（对象存在、字段有值、条目存在）、对象版本时点匹配。
删 `data_per_subquestion` 义务文本里的原因清单（查询未执行 / 原因未定位 / 服务不可用）：查询未执行 → 输入无效指向规划；原因未定位 → 缺证 + 未定位问题；服务不可用 → 执行失败，是工具轴的单位。

**模型能力**（该次输入 → 该次输出）。输出必须：忠实于输入、不添加输入没有的东西、决策与输入一致、遵循输入写明的契约。
→ 输出忠实（不改义、不丢关键信息）、不编造、工具调用决策一致、输出契约遵循。
把现有 `output_faithful` 拆成"忠实"和"不编造"两条：按 §3.3 规则 2，"不编造"不依赖缺失的输入，必须能独立判。

**上下文管理**（一处产出 → 下一处输入）。传递必须：原义到达、组装正确、历史与缓存来源正确、交付完整。
→ 传递保留原义、模型输入组装、历史与状态使用、交付保留原义。现有四条对应。删 arrives_intact 里"上游本就错误而被如实转交不算本项偏差"的分句：由 §3 对照取代。

## 9. 需求里的 P1–P7 在本协议下的输出

| # | 现象 | 输出 |
|---|---|---|
| P1-A | 没发查询，数据没拿到 | 规划轴：工作覆盖 × Q1 没做到 → 问题#1 归规划。知识轴：数据存在 × Q1 输入无效 → #1；若无其他有效取数，verdict untested |
| P1-B | 查了，数据源确实没有 | 知识轴：数据存在 × Q1 没做到 → 问题归知识，problematic |
| P2 | 返回为空，看不清工具还是库 | 两轴单位均"缺证（产出不符、输入有效性不明）"→ 两轴 not_evaluable；一条问题，归因未定位{工具, 知识} |
| P3 | 提示被系统丢了，模型答错 | 上下文轴：传递保留原义 没做到 → 问题归上下文。模型轴：输出忠实 输入无效 → 该问题；不编造 做到 → verdict sound，组成显示 1 输入无效 |
| P4 | 有没做到也有缺证 | problematic；组成写明 n 项缺证 |
| P5 | 全做到但有缺判准 | sound；组成写明 n 项缺判准，判准清单并列 |
| P6 | 评测器输出不合法 | 运行 error，不进任何单位取值 |
| P7 | 聚类输入是整段 reason | 聚类成员改为问题记录 |

## 10. 分层样例

形式：轴 → verdict → 子能力 → 样例。各轴 verdict 层相同，只列有代表性的分支。

知识数据

```text
problematic
  ├── 数据存在         ── 业务材料说这张保单应存在，库里没有
  └── 对象版本时点匹配 ── 要 2024 年版条款，返回的是 2023 年版
not_evaluable
  └── 数据存在（缺证） ── 返回为空，看不清工具还是库；问题归因未定位{工具, 知识}
sound
  └── 组成：Q2 做到；Q1 输入无效 → 规划#1
untested
  └── 所有子问题都没发查询；组成：2 项输入无效 → 规划#1、#2
not_applicable
  └── 本轮问题不需要外部数据
```

模型能力

```text
problematic
  ├── 输出忠实         ── 输入说"未查询到"，输出写"已失效"
  ├── 不编造           ── 输入没有出生日期，输出写了一个
  ├── 工具调用决策一致 ── 输入已有有效结果，无理由再查
  └── 输出契约遵循     ── 输入写明 JSON，输出自然语言
sound
  └── 组成：不编造 做到、决策 做到；输出忠实 输入无效 → 上下文#1（提示丢失）
untested
  └── 唯一一次模型调用的输入被系统弄坏，所有子能力输入无效 → 上下文#1
not_applicable
  └── 本轮走直连，没有模型调用
```

意图理解

```text
problematic
  ├── 对象与字段一致 ── "退保金额"被表达成"保费"
  ├── 子问题均识别   ── 用户问两个，只表达一个
  ├── 约束保留       ── 用户限定 2024 年，内部没带时间
  ├── 指代解析       ── 历史在，"那个保单"仍解析到错的一张
  └── 歧义识别       ── 历史里有两张，内部直接选定一张当事实
sound
  └── 组成：四项做到；指代解析 输入无效 → 上下文#2（历史未注入）
not_applicable
  └── 指代解析：用户没用指代
```

## 11. 反面情况（永远不许）

```text
1. 用"这归别的轴"当本轴通过的理由，却指不出那条上游问题        ✗
2. 输入无效时判 sound                                            ✗
3. 把"应发生而没发生"判成 not_applicable                         ✗
4. verdict 不带组成单独出现                                      ✗
5. 评测器失败写成缺证                                            ✗
6. 为了"结果坏至少一轴 problematic"把未定位硬判到某一轴          ✗
7. 义务文本里自带归属分句（归数据源 pass / 查不明 fail 之类）    ✗
8. 一条问题记录装多个独立问题                                    ✗
```
