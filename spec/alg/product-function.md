> 状态：草稿。和 `spec/alg/fulfilled.md` 同级，回答另一件事。
> 不改 fulfilled 三态，不进入 Judge 产出，不进入结果表词表。
> 现在只用于对照阅读；以后若要看见，再另定派生列，不另开判定。

# 第一章：Spec 标准

## 1. 我们在评什么

三个角色同 `fulfilled.md`。

`fulfilled.md` 只看一件事：系统有没有帮用户办成想办的事。

本协议只看另一件事：

```text
用户要办的这类事，现在是不是这个产品已经有的功能？
```

```text
用户要办的这类事
  = 从用户视角说的事情种类
    例："按姓名找客户"、"按险种找客户"、"做盘客"
  ≠ 这一次具体值能不能搜出来
  ≠ 字段 / 接口 / 操作符支不支持
  ≠ 用户要的结果这次有没有拿到
  ≠ 系统有没有说出"暂不支持"
```

两件必须分开答：

```text
fulfilled.md     用户要的事，办成了没有？
本协议           这类事，现在是不是产品已经有的功能？
```

任何一张表、一个标签、一句结论，都不能同时回答这两件。
本协议不替代 `fulfilled.md`，也不并进它的三态。

## 2. 三个状态

### 2.1 有这项功能

产品今天已经把这类事当作自己的功能来做。必须同时满足：

1. 这类事落在产品定位里；
2. 有实据证明产品今天已经立起这项功能——不是"应该有"，也不是"以后会有"；
3. 评的是事情种类，不是这一次实例成不成功。

### 2.2 没这项功能

产品定位还管这类事，但今天还没把它立成功能。

不是职责外，不是完全无关，不是这次没搜到。
是：这类事还在产品该管的范围内，只是当前功能上还没有它。

### 2.3 说不清

该给个说法，但没法确定"有 / 没有"。差在哪儿必须写清：

| 差在哪儿 | 什么时候出现 |
|---|---|
| 不在定位里 | 这类事产品本来就不管 |
| 完全无关 | 跟产品完全不沾边 |
| 依据不充分 | 分不清在不在定位里，或分不清立没立住 |
| 输入坏 | 用户输入本身不可用，认不出要办的是哪类事 |

三个硬前提（防止变成垃圾桶）：

1. 不能因为"这次没办成"就说没这项功能，也不能因为"这次办成了"就说有这项功能；
2. 必须写清差在哪儿；
3. 是临时态，不能当永久结论。

## 3. 判断顺序

```text
第一步：用户要办的是哪类事？
  从用户视角写种类，不从字段、接口、操作符写
  一件事里若有几类，分开看
  认不出种类 → 说不清（输入坏 / 依据不充分）

第二步：这类事还在不在产品定位里？
  这里的"产品定位"是这个产品管哪类事，
  不是资料定位，也不是"放对地方"
  ├─ 不在定位里 → 说不清（不在定位里）
  ├─ 完全无关   → 说不清（完全无关）
  ├─ 分不清     → 说不清（依据不充分）
  └─ 在定位里   → 第三步

第三步：产品今天有没有把这类事立成功能？
  ├─ 有实据已经立住 → 有这项功能
  ├─ 有实据还没立住 → 没这项功能
  └─ 分不清         → 说不清（依据不充分）
```

一件事里有几类时，整体只用于对照阅读，不进结果表：

```text
任何一类核心事没这项功能 → 整体没这项功能
任何一类核心事说不清     → 整体说不清
全部核心事都有这项功能   → 整体有这项功能
```

不得拿已经有的那类，去盖住没有的那类。

## 4. 和邻题的边界

| 问题 | 在哪 | 问的是 | 和本协议 |
|---|---|---|---|
| 办成了没有 | `fulfilled.md` | 用户要的结果这次有没有拿到 | 不问结果 |
| 该不该由这个产品管 | authority 职责 | 应不应该管 | 不问应该 |
| 这份资料能不能当尺子 | `material-positioning.md` | 资料站在哪 | 不评资料 |
| 这个值 / 这种说法现在到不到得了 | positioning 空间、authority 表达 | 这一次实例的空间 | 不评实例 |
| 字段 / 操作符 / 接口支不支持 | 系统实现事实 | 实现上可不可达 | 不评实现 |
| 系统有没有说出"暂不支持" | 话术 | 态度、说明 | 既不能证明有，也不能证明没有 |
| 系统尽力了没有 | 派生阅读 | 两轴对照后的读法 | 不是本协议的状态 |

下面这些问法一律不准用来替代本协议的问题：

- "今天办不了吗"
- "系统能不能做"
- "系统尽力了吗"
- "系统有没有正确承认还不支持"
- "这件事放对地方了吗"
- "这次处置站不站得住"

这些问法都会在不同语境里滑向另一件事：办成了没有、该不该管、这次值合不合法、态度好不好。
对它们答"是"或"不是"，都可能被带到相反结论。

## 5. 什么叫"这类事"，什么叫"已经有的功能"

**这类事**：用户要办的事情种类。只问种类，不问这一次的具体值、这一次搜没搜到、这一次表达得对不对。

**已经有的功能**：产品今天已经把它当作自己的一项功能。证据必须是产品定位、功能说明、业务方确认过的功能清单这类"产品自己认账"的材料。

不能当证据的：

- 系统这次碰巧给了结果
- 系统这次没给结果
- 系统说了"暂不支持"
- 字段表里有或没有某字段
- 操作符支不支持
- `is_supported` / 能力开关
- 判定模型自己的松紧
- 长尾 bad case 里高频出现

"应该有但还没有"不是"有这项功能"，也不是 fulfilled 的"办成了"。
它落在本协议的"没这项功能"。fulfilled 仍按自己的协议去判"没办成"或"说不清"。

## 6. 两轴怎么读

本协议不改 fulfilled。对照时只能这样读：

| | 有这项功能 | 没这项功能 | 说不清 |
|---|---|---|---|
| 办成了 | 现有功能里办成了 | 现有功能之外却被看成办成了 | 先别用本协议解释 |
| 没办成 | 现有功能里没办成 | 需求没满足，但这不是现有功能 | 先别用本协议解释 |
| 说不清 | 功能有了，办没办成看不清 | 功能也没有，办没办成也说不清 | 两轴都看不清 |

"尽力了"只是「没办成 × 没这项功能」的一种读法，不是状态，不得写回任何标签。

"过严"常常是「没办成 × 有这项功能」：功能已经有了，却按不该加的门槛把现有功能判成没办成。也不得写成状态。

"互有对错"是两轴对照后两边都不干净，不是 fulfilled 的第四态。

## 7. 反面情况（永远不许）

```text
1. 给 fulfilled 加第四态来表达本协议                         ✗

10. 从长尾 bad case 反推功能种类                            ✗
11. 拿已经有的那类功能盖住没有的那类                        ✗
12. 把"尽力了""过严"写成正式状态                           ✗
```

# 第二章：怎么落地

## 8. 不加枚举，不加新标签

| 做法 | 为什么 |
|---|---|
| 给 fulfilled 加一个枚举值 | 一个标签回答两件事；和 `spec/info-volume.md` 三态冲突；归因按三态走会被打乱；"没办成"的业务含义会被改掉 |
| 新增一个让 Judge 填的标签 | 变成第二个判定；两问会抢解释权；会过拟合长尾集 |
| 先写本协议，在冻数据上投影 | 要做的：先能对照着读，不改判定 |
| 以后若要看见，再加派生列 | 派生列不是 Judge 产出，不进 prompt，不改 fulfilled |

派生列如果以后要加，也只是把本协议三态单独列出来，供人对照阅读。
它不是 fulfilled 的新值，也不是模型新填的判定。

## 9. 现在做 / 现在不做

现在做：

- 留下本协议；
- 用已有对照集做投影，不跑新模型；
- 只改阅读，不改判定。

现在不做：

- 不改 Judge prompt；
- 不改结果表；
- 不改归因；
- 不改 authority 词表；
- 不上线任何新字段。

## 10. 验收（协议本身）

- 任何案子都能落进三态之一；说不清必带差在哪儿；
- 能单独回答，不需要先看 fulfilled；
- 换一批非长尾数据，这个问题仍然成立；
- 没有一条规则是"这类 query 就判没有"；
- 对照阅读能把"需求没满足但不是现有功能"和"现有功能里没办成"分开，且不改 fulfilled。
