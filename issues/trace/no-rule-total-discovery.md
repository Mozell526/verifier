# Discovery — 第二问的规则化残留

章程：`issues/charter-no-rule-total.md`
本轮不重判 006–038，不改协议，不加字段，不代拟对外句。

## 1. 用户这一轮到底否什么

上一轮（032–034）已经锁了五条：

1. 第二问单位是「这种事 × 产品里站立的那一档」
2. 答第二问时不看这一次交付
3. 「现成没有」进不了漏做，也进不了职责外 / 对象未成形
4. 第一问办成了，不能自动排除「现成没有」
5. 023 的 2×2 只是交叉表，不是第二问

用户这轮不是再换一句口语。用户加了三道闸：

- 不要有规则化
- 排除所有可能的歧义
- 能覆盖所有可能出现的情况

这三道闸打在 033 的操作化上，不是整包推翻五条。

## 2. 协议里第一问为什么不是规则化

`spec/alg/fulfilled.md` §1：

> 我们：评测系统（Judge），只看一件事——系统有没有帮用户办成想办的事。
>
> 第一层：用户要的事办成了没有？
> 第二层：手里的材料够不够回答第一层？

§2.2 没办成「不区分原因」，并把「功能本身未实现，但用户期望已提出」收进没办成。

所以第一问是原则，不是类型表：

```text
对象 = 用户要的事（这一次认下的那一件）
单位 = 这一次请求 × 这一次交付
不看 = 产品把这件事立住了没有
不区分 = 没给到的原因
出口 = 办成了 / 没办成 / 说不清
全函数 = 任意一次请求+交付，必落三态之一
```

§2.3 的「差在哪儿」是说不清的理由，不是先分类再查表的门。
§3 判断顺序是评测员怎么走到三态，不是把用户要的事预先切成姓名 / 年 / 天气。

`spec/alg/authority.md` §1 / §8.2 把另一件产品事实拆走：

> Authority Agent 只解决“标准是否确定”，不判断某个实际输出是否满足用户要求。
> Authority 只裁决“有没有这个能力/属不属于职责”，不裁决“本次输出是否达标”。

`authority.md` §8.3：职责内能力缺失 + 实际达成 → 办成了。
所以协议里本来就允许：第一问办成了，产品事实仍可以是「没立住」。

`spec/alg/material-positioning.md` 不变量 1：

> `current_behavior` 类 Decision 只能解释系统现状，永远不能代替 `normative_rule`
> 或 `external_fact` 类 Decision

所以「这一次没给到 / 这一次字段空」不能冒充「产品没把这件事立住」。

## 3. 033 操作化为什么会滑成规则化

033 Consensus 第 4 条原文：

> 认「这种事」是哪一类，只准看这一次请求。

再加上对照表把四例写成四类，再加上「那一档」这个词。

三件叠在一起，评测员会被教会这套手续：

```text
1. 先把请求分进类型：姓名 / 投保年 / 格式外 / 天气
2. 再按类型查「产品有没有那一档」
3. 新形状来了，就再加一行
```

这正好踩中章程对规则化的定义。

它也踩中「覆盖」的假读法：以为覆盖 = 把这四类写全。
四类写全了，也盖不住：合取、别的表面才有、文档有运行时从来没有、在建、租户差、对象两可、相邻近义、部分立住、以前有现在拆了、完全没见过的新形状。

这些新形状不该变成新行。它们必须仍落在同一套三态里。

## 4. 正确原则（内部结构，不是对外题面）

两问同级。对象同一件。只换证据单位。

```text
第一问（已经有）
  只看一件事：这一次，用户要的结果有没有给到
  对象：用户要的事
  单位：这一次请求 × 这一次交付
  不看：产品把这件事立住了没有
  不区分：没给到的原因
  出口：办成了 / 没办成 / 说不清
  全函数：任意一次请求+交付 → 三态之一

第二问（出口还没有）
  只看一件事：用户要的这件事，产品把它立成自己会做的事了没有
  对象：仍是第一问那件「用户要的事」
        不得另立类型表
        不得切得更粗或更细
  单位：这件事 × 产品事实
  产品事实：这个产品把这件事立成自己会做的事了没有
            依据不能是这一次交付
            也不能是 catalog / is_supported / current_behavior
  不看：这一次给没给到
        这一次承不承认 / 尽没尽力
        库存字段表
        预置类型表
  不区分：没立住的技术原因（缺字段 / 缺接口 / 半成品 / 旁路）
  出口（内部手柄，不是对外题面）：
        立住了
        没立住   = §8.3 职责内能力缺失的投影
        说不清   必须写清差在哪儿
                 职责外 / 完全无关
                 对象未成形 / 输入坏
                 依据不充分（分不清「没立住」还是「立住了、这一次没用」）
                 不得用说不清装长期没立住
  全函数：任意一次「用户要的事 × 产品事实」→ 三态之一
          新形状不必加新行

隐藏前提（不单独对外问）：
  职责内由 Authority 先裁。
  和第一问「办成了必须职责内」同一层。
```

「立住了 / 没立住 / 说不清」只是本轮内部手柄，用来证明三态能按单位切开。
不宣布采用这几个字当对外题面。033 的「现成有 / 现成没有」同样仍是手柄，不升级。

## 5. 穷尽测试（碰撞针，不是类型表）

每一针只用来打原则。打完就扔掉，不写进定义。

| 针 | 第一问看什么 | 第二问看什么 | 原则必须落到 | 若变成规则就会写成 |
|---|---|---|---|---|
| 漏了姓名 | 这回没给到 | 产品已把「按姓名找」立住 | 没办成 × 立住了 | 「姓名类 → 现成有」 |
| 投保年缺口（形态） | 这回没给到 | 份内该立、没立 | 没办成 × 没立住 | 「年类 → 现成没有」 |
| 格式外编号 | 事还没立成可谈的对象 | 还不能谈立住 | 说不清 × 说不清 | 「格式外类」 |
| 查天气 | 不是这个产品的事 | 还不能谈立住 | 说不清 × 说不清 | 「天气类」 |
| 没立住，但这回绕过给到了 | 给到了 | 仍没立住 | 办成了 × 没立住 | 「给到了就立住了」 |
| 立住了，而且这回用上了 | 给到了 | 立住了 | 办成了 × 立住了 | — |
| 用户要的是合取（姓名且年） | 整件给没给到 | 整件立住了没有 | 不得拆成两件再查表 | 「先拆字段」 |
| 别的表面才有 | 这产品给没给到 | 这产品立住了没有 | 不得拿兄弟系统冒充 | 「公司会就不会」 |
| 文档有、这一次从来没交过 | 看这一次交付 | 不得用这一次空交去证没立住 | 材料不够就说不清 | 「字段空 = 没立住」 |
| 在建 / 半成品 | 这回给没给到 | 现在立住了没有 | 不新开「即将有」 | 「进度类」 |
| 这个租户没有、产品对这类用户本就没立 | 这回给没给到 | 对这类用户立住了没有 | 一次权限事故 ≠ 没立住 | 「租户表」 |
| 用户要的事两可 | 说不清 | 说不清 | 两个问都说不清 | 「先猜一种」 |
| 相邻近义（昵称 vs 姓名） | 是否同一件「用户要的事」 | 不得另立近义规则 | 材料不够就说不清 | 「同义词表」 |
| 只立住一部分 | 第一问不许第四态 | 第二问也不许「立住一半」 | 整件没立住，或说不清 | 「部分分」 |
| 以前有、现在拆了 | 这回给没给到 | 看现在的产品事实 | 不新开「曾经有」 | 「历史类」 |
| 完全没见过的新形状 | 同一套第一问 | 同一套第二问 | 必落三态之一 | 「再加一行」 |

任一针若只能靠「加一行类型」才能落格，原则失败。

## 6. 换语境翻面测试

同一案子，先只看这一次会话，再只看产品事实。第二问答案不得变。

会翻面的读法（必须判死刑）：

- 「立住了没有」= 这回给到了没有
- 「这种事」= 先分进姓名/年/天气
- 「产品事实」= 这一次字段空 / is_supported=false / 系统说了暂不支持
- 「说不清」= 长期份内缺口的垃圾桶

不翻面的读法（本轮留下）：

- 对象始终是第一问那件「用户要的事」
- 证据始终是产品把它立住了没有
- 这一次交付只许用来答第一问

- 不改 schema
