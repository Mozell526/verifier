# Discovery — 需求轴 vs 产品可支持轴（2026-08-15）

用户把上一轮开关 2（去年）和 3（格式外/称谓）看成可能同一类：
业务需求没完全满足，但按当前产品能力和已有资料，系统也算尽力了。
想要的不是 fulfilled 这种「办成了没有」，而是产品功能定位以内、能明确指出「当前尚未支持」的一层。
不要做成纯 IT 能力审计。

## 现行协议已经钉死的事

1. `fulfilled.md` §1：Judge 只看一件事——系统有没有帮用户办成想办的事。两层是「办成了没有」和「材料够不够回答第一层」，没有第三层「当前能力下是否尽到产品位」。
2. §2.2 / §4.1 / §5 / §7.1 / D3：职责内能力缺失 + 期望未达成 = 没办成；如实拒绝 ≠ 办成。词表「不新增第四态」。
3. `info-volume.md`：整体三态不引入 partial。
4. `authority.md` §1 / §2 / §8.3：Authority 只裁决标准是否确定（有没有这能力 / 属不属于职责），不判断 fulfilled。消费时「职责内能力缺失」仍回到 F/NF。
5. `material-positioning.md`：`inlive_boundary` 回答空间里有什么，不回答办成了没有；`current_behavior` 不能当正式规则。
6. Runtime：`BusinessExpectation.blocking` 是「这维缺了是否阻断核心」；`required_capabilities` 是期望声明需要什么；`FulfillmentAssessment` 只有 `status` + `authority_tool_call_ids`，没有产品支持处置字段。`impl/core/schema/judge.py` 写明项目特有 `boundary_decision` 不下沉进通用三态。

## 碰撞（只作举例，不重判）

- 开关 2：核心对象已交付，附加维「去年」当前不支持且已提示。需求轴：这一维没办成。产品轴：这是定位内尚未支持。
- 开关 3：格式外编号 / 称谓未形成可执行产品对象。需求轴：不能假装办成，也不能按「本可支持却没给」打 NF。产品轴：这不是「尚未支持」，是「不是产品对象 / 空间外」。

二者共享「不能用尽力了换 F」，但不共享「尚未支持」。
