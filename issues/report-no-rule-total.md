## 上一轮为什么还会被读成规则

不是单位又切错了。是 033 把单位写成了手续。

```text
认「这种事」是哪一类
+ 产品里站立的那一档
+ 姓名 / 年 / 格式外 / 天气 四行对照
= 先分进预置类型，再按类型查表
```

「认用户要什么」是 `fulfilled.md` 已经在做的一步：把一件事认出来。
「认哪一类」把这一步滑成编类型。
「那一档」听起来像可查的槽位。
四行表本是碰撞针，贴在这种用词旁边就会升级成查表键。

新形状一来，评测员就会想再加一行。这就是规则化，也是假覆盖。

## 正确抽象（和「办成了没有」同一层）

两问同级。对象同一件。只换证据单位。

```text
第一问（已经有）
  只看一件事：这一次，用户要的事办成了没有
  单位：这一次请求 × 这一次交付
  不看：产品把这件事立住了没有
  不区分：没给到的原因
  出口：办成了 / 没办成 / 说不清
  任意一次请求+交付，必落三态之一

第二问（出口还没有）
  只看一件事：用户要的这件事，产品把它立成自己会做的事了没有
  对象：仍是第一问那一件
        不得另立类型表
        不得为了更好答第二问把对象切粗或切细
  单位：这件事 × 产品事实
  计算位置：Authority 已经裁完的能力/职责判断，及其依据资料
  不看：这一次给没给到
        这一次承不承认 / 尽没尽力
        库存字段表
        预置类型表
  不区分：没立住的技术原因
  出口（内部手柄，不是对外题面）：
        立住了 / 没立住 / 说不清
  任意一次「用户要的事 × 产品事实」，必落三态之一
  新形状不必加新行；加新行就是规则化
```

认对象：只准看这一次请求，把「这一件」认出来。
答第二问：不准看这一次交付。

职责内仍是隐藏前提。评测员不先答「该不该管」。

「没立住」= 协议里已经具名的那一格：职责内、能力缺失。不是新发明的第四态。
第一问办成了，不能自动排除「没立住」。协议原文就允许：能力缺失，但这回实际给到了，第一问仍是办成了。

「立住了 / 没立住」只是理事会内部手柄。不是对外题面，也不宣布采用。

## 覆盖怎么算盖住，怎么不算

覆盖 = 出口穷尽。不是把能想到的情况列完。

所以：

- 合取、别的表面才有、文档有这一次空、在建、一次权限事故、对象两可、只立住一部分、完全没见过的新形状
- 全部还走同一套三态
- 材料不够就说不清，且必须写差在哪儿
- 说不清不得装长期没立住
- 不新开「即将有 / 立住一半 / 曾经有」

这些形状只用来打原则。打完就扔。写成类型行，原则当场失败。

## 「尽力了」和其他角度各是什么

| 角度 | 它其实是 | 能不能当第二问 |
|---|---|---|
| 办成了没有 | 第一问 | 已经是第一问 |
| 产品把这件事立住了没有 | 第二问 | 能，而且只有这一件 |
| 尽力了 | 两问交叉后，没办成 × 没立住 的观感 | 不能当主问 |
| 有没有正确承认尚未支持 | 第三问：披露打分 | 不能当主问 |
| 该不该管 | Authority 已经在问的隐藏前提 | 不能单独对外问 |
| 今天就办不了吗 / 是不是 | 用第一问的字去点第二问 | 必然翻面 |
| 先分成姓名/年/天气再查表 | 规则化 | 不能当手续 |
