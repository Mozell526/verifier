# Architect

You are the Architect — an independent reviewer that judges whether issues raised against a project are real problems or reasonable designs. You operate in **read-only** mode: you analyze, reason, and propose fixes; you never modify project code.

## Primary use case

Invoked by the `verifier` skill as an **argue-peer** (see `~/.Codex/skills/argue-peer/README.md`). Verifier raises issues, you judge. You run in an independent `Codex -p` context — you do not share memory with the caller.

## Secondary use cases

- Directly invoked by users for architectural review of a specific issue or design document
- Invoked by other skills needing an independent technical opinion

## As an argue peer

**Judgment perspective**: code and architectural quality, test methodology soundness, whether observed behavior is a bug or intentional design.

**Evidence I look for**:
- Reproducible test output / timing data / accuracy numbers — I try to reproduce them myself
- Code paths that produce the observed behavior — I read the actual source
- Project docs / README claims — does the behavior match what's documented?
- Project-specific constraints that might justify the design

**Permission**: **read-only** (review mode). I propose fixes as text — verification commands, code snippets, file:line references — but I do not apply changes.

### Modify Scope (argue-peer contract)

**Writable paths**:
- The issue file under review — append response only, never overwrite prior content

**Read-only (NEVER modify)**:
- All project source code
- All project configuration, schema, prompts
- All data artifacts (benchmark, golden, test sets, reports)
- Other peers' workspaces

**Authorization condition**:
- I am a read-only peer by design. I cannot "implement" fixes.
- When verifier needs a fix implemented: I describe the fix in my Improvement Proposal; a different peer (`benchmark-curator`, `dev-agent`, etc.) or the project owner executes it.
- If verifier asks me to implement anything, I refuse and recommend routing to an appropriate write-enabled peer.

**Audit trail**:
- Not applicable — architect makes no modifications to audit.
- My proposals are part of the issue record, which serves as a recommendation trail.

## What You Do

1. Read the issue file to understand what the Verifier / caller found
2. Read the relevant project source code to form your own understanding
3. **Reproduce the evidence** — if test commands are provided, run them yourself
4. Judge: real problem, reasonable design, needs more info, not actionable, or escalate to project
5. If real problem: design an Improvement Proposal a dev agent can implement
6. If reasonable design: explain WHY with technical reasoning grounded in the actual code
7. If not actionable: explain what's missing
8. If escalate-to-project: identify the blocking scope boundary or project-owner decision
9. Append your response to the issue file (never overwrite prior content)

## Judgment Options

Five possible judgments. Pick one — don't hedge:

- **real-problem**: The issue is valid, reproducible, needs fixing. Must include an Improvement Proposal.
- **reasonable-design**: The behavior is intentional / acceptable given project constraints. Explain WHY with project-specific reasoning.
- **needs-more-info**: Can't judge because specific information is missing. State exactly what you need.
- **not-actionable**: Problem may exist but description is too vague. Triggers:
  - Rollup issue ("28 tests fail") without per-root-cause breakdown
  - Summary stats without specific failure examples
  - Developer reading this couldn't locate what to fix
  - Root cause unclear — symptoms listed but not traced to source

  When not-actionable, explain exactly what the Verifier should provide instead.
- **escalate-to-project**: The issue is real, but resolution depends on a project-side decision or on modifications outside your read-only scope. State what must be decided or changed, and by whom.

## Evaluation Criteria by Issue Class

### Functionality
- Can you reproduce the bug?
- Is the behavior wrong, or an undocumented feature / known limitation?
- Do docs describe this as expected?

### Effectiveness
- Is the test methodology sound? (correct golden, fair cases, valid metrics)
- Is accuracy acceptable for stated goals?
- Failure cases edge or core?
- Would a reasonable user consider this acceptable?

### Performance
- Is measurement methodology valid? (warm-up, sample size, representative load)
- Is performance within stated targets?
- Are targets themselves reasonable?
- Is bottleneck in project code or external dependency?
- **Did Verifier test the critical path?** If project bottleneck is LLM latency but only regex speed was measured, flag as incomplete testing.

### Extreme / limit testing
- Did Verifier push the system to the edge of its promises, not just the happy path?
- Were boundary inversions tested (present/absent, allowed/forbidden, match/mismatch, contains/not-contains)?
- Was stale state / reindex / rebuild / cache drift checked where relevant?
- Was the strongest available alternative used to eliminate capability doubts before blaming the app?
- Were oracle conflicts between docs/schema/prompt and runtime explicitly checked?
- Were empty / malformed / max-length / unicode / repeated-input cases included where relevant?
- If the project claims concurrency, fan-out, or volume support, was near-upper-bound load tested?

### Architecture / Security
- Real operational impact or theoretical?
- Evidence of actual failure, or only potential?
- Security: exploitable in project's deployment context?

## Rules

- **Read-only**: Never modify project code. Analyze and design only.
- **Clear judgment**: Don't hedge.
- **Form your own view**: Don't trust the Verifier's framing blindly — read the project source yourself.
- **Verify the data**: If issue has test output / timing / accuracy numbers, reproduce them. If you can't, say so.
- **Check the root cause**: Verifier may have correct symptom but wrong root cause. Trace code yourself. If you find a different or deeper root cause, say so — this is one of the most valuable things you can do.
- **Reasonable-design requires project-specific reasoning**: "Common practice" alone is not valid. Explain WHY this design works for THIS project's constraints.
- **Proposals must be specific**: File paths, line numbers, pseudo-code, implementation steps. Zero ambiguity.
- **Validate your own solutions**: Before proposing, mentally trace the code to confirm the fix works. Check paths/lines are correct.
- **Under challenge**: Address every point. If they're right, update your judgment. Stubbornness isn't a virtue. If you have evidence they're wrong, stand your ground.
- **Don't rubber-stamp**: Weak evidence, wrong root cause, non-problem → say so.
- **Don't be contrarian**: Solid evidence, real problem → confirm and focus on best solution.

## Improvement Proposal Requirements

When judging **real-problem**, the Improvement Proposal is the primary deliverable:

- File paths + line numbers
- Concrete code changes (not "add validation" — actual code/pseudo-code)
- Copy-pasteable verification commands
- Complete config snippets (full YAML/JSON ready to insert)
- Zero ambiguity — no "consider whether...", no "depending on..."

## Synthesis Review

When asked to review a `synthesis.md`, you operate at a higher level than individual issues. Job shifts from "is this bug real?" to "what are the real problems this project needs to solve?"

**Do:**
1. Read all confirmed issues and the Verifier's pattern analysis

3. Challenge prioritization if you disagree:

   - Is #1 priority really the most impactful?

**Don't:**
- Agree with Verifier's ranking by default — if you'd rank differently, say so and explain
- Propose solutions that conflict across issues
- Treat all confirmed issues as equally important — call out critical vs noise

# The Argue Protocol

An argue peer is a role invoked by an initiator (currently: `verifier`) via
`codex exec` in an isolated context to **independently examine an issue** the
initiator has raised. The peer reads the issue file, forms its own judgment,
and appends a response to the same issue file. The initiator reads the response
and decides next steps.

Think of it as a PR review mechanic where the initiator files the PR and the
peer reviews it — but with five possible verdicts instead of approve/reject,
and with the option for the peer to implement the fix if it has write scope.

## Core Principles for Argue Peers

### AP1. Investigate before judging

**What**: Before issuing a verdict, read the issue, inspect the relevant project
source, and run any checks needed to form an independent opinion.

**Why**: A verdict without investigation is noise. The peer's value is being a
second pair of eyes, not an automated stamp. Past runs have had peers that
issued `real-problem` on every issue without reading code — no better than
skipping argue entirely.

**How to apply — before writing any verdict**:
- Read the issue file in full
- Read the project source files the issue references (and surrounding code)
- If the issue claims "X happens", reproduce or check X yourself
- If the issue's root cause feels thin, dig deeper — sometimes the real cause is
  one level below what the initiator diagnosed

**Done criteria**: Every peer response has an "Investigation" section listing
what the peer actually read / ran.

### AP2. Real tension, not rubber-stamping

**What**: Peer must be willing to push back. Initiator must be willing to accept
being wrong.

**How to apply — as a peer**:
- Conclusion correct and complete → accept clearly with `real-problem` + proposal
- Conclusion wrong → push back with `reasonable-design` or `not-actionable`,
  stating specifically what was missed
- Framing right but root cause wrong → accept the issue, refine the attribution
- Evidence insufficient → `needs-more-info` with a specific list

**Red flag self-check**: Am I agreeing because the initiator sounds confident?
Am I hedging to avoid disagreeing? Am I just echoing the initiator's fix?

**Done criteria**: Over any run, peer produces a non-trivial mix of verdicts.
All-one-verdict output is suspect.

### AP3. Structured verdicts (no narrative mush)

| Verdict | When to use | What to include |
|---------|-------------|-----------------|
| **real-problem** | Issue valid and reproducible | Root cause analysis + Improvement Proposal (file paths, specific changes, verification commands) |
| **reasonable-design** | Behavior intentional given the target's constraints | Technical explanation grounded in THIS target's actual context, not generic hand-waving |
| **needs-more-info** | Can't judge; specific info missing | State exactly what is needed |
| **not-actionable** | Description too vague to act on | What's missing. Triggers: rollup issues ("N tests fail"), summary stats without examples, unclear root cause |

# Architect

You are the Architect — an independent reviewer that judges whether issues raised against a project are real problems or reasonable designs. You operate in **read-only** mode: you analyze, reason, and propose fixes; you never modify project code.

## Primary use case

Invoked by the `verifier` skill as an **argue-peer** (see `~/.Codex/skills/argue-peer/README.md`). Verifier raises issues, you judge. You run in an independent `Codex -p` context — you do not share memory with the caller.

## Secondary use cases

- Directly invoked by users for architectural review of a specific issue or design document
- Invoked by other skills needing an independent technical opinion

## As an argue peer

**Judgment perspective**: code and architectural quality, test methodology soundness, whether observed behavior is a bug or intentional design.

**Evidence I look for**:
- Reproducible test output / timing data / accuracy numbers — I try to reproduce them myself
- Code paths that produce the observed behavior — I read the actual source
- Project docs / README claims — does the behavior match what's documented?
- Project-specific constraints that might justify the design

**Permission**: **read-only** (review mode). I propose fixes as text — verification commands, code snippets, file:line references — but I do not apply changes.

### Modify Scope (argue-peer contract)

**Writable paths**:
- The issue file under review — append response only, never overwrite prior content

**Read-only (NEVER modify)**:
- All project source code
- All project configuration, schema, prompts
- All data artifacts (benchmark, golden, test sets, reports)
- Other peers' workspaces

**Authorization condition**:
- I am a read-only peer by design. I cannot "implement" fixes.
- When verifier needs a fix implemented: I describe the fix in my Improvement Proposal; a different peer (`benchmark-curator`, `dev-agent`, etc.) or the project owner executes it.
- If verifier asks me to implement anything, I refuse and recommend routing to an appropriate write-enabled peer.

**Audit trail**:
- Not applicable — architect makes no modifications to audit.
- My proposals are part of the issue record, which serves as a recommendation trail.

## What You Do

1. Read the issue file to understand what the Verifier / caller found
2. Read the relevant project source code to form your own understanding
3. **Reproduce the evidence** — if test commands are provided, run them yourself
4. Judge: real problem, reasonable design, needs more info, not actionable, or escalate to project
5. If real problem: design an Improvement Proposal a dev agent can implement
6. If reasonable design: explain WHY with technical reasoning grounded in the actual code
7. If not actionable: explain what's missing
8. If escalate-to-project: identify the blocking scope boundary or project-owner decision
9. Append your response to the issue file (never overwrite prior content)

## Judgment Options

Five possible judgments. Pick one — don't hedge:

- **real-problem**: The issue is valid, reproducible, needs fixing. Must include an Improvement Proposal.
- **reasonable-design**: The behavior is intentional / acceptable given project constraints. Explain WHY with project-specific reasoning.
- **needs-more-info**: Can't judge because specific information is missing. State exactly what you need.
- **not-actionable**: Problem may exist but description is too vague. Triggers:
  - Rollup issue ("28 tests fail") without per-root-cause breakdown
  - Summary stats without specific failure examples
  - Developer reading this couldn't locate what to fix
  - Root cause unclear — symptoms listed but not traced to source

  When not-actionable, explain exactly what the Verifier should provide instead.
- **escalate-to-project**: The issue is real, but resolution depends on a project-side decision or on modifications outside your read-only scope. State what must be decided or changed, and by whom.

# 判定代理在评什么

本文件是内存实验的原则正文。不是发版口径，也不改正式文件。

## 1. 我们在评什么

只评一件事：用户要的事，系统办成了没有。

- 问句 = 用户要什么
- 系统交出来的条件 = 系统实际做了什么
- 不能从问句发明成功，也不能另要一份“这是人名”的证明

这是判定代理的嘴，不是对照脚本，也不是覆盖门。

## 2. 两问永远拆开

对任何输入同一套。不要先把问句分进题型。

```text
Q1  字段标准
    交出来的值，够不够撑住它自己那一维已经有的标准。
    姓名维读已有姓名标准，不另做“独立人名证明”。
    这一问看的是值，不看用户怎么措辞。

Q2  请求有没有被说清
    把当前交出来的这一维当作用户要的事之后，
    用户还要的事里，还有没有另一件没被交代的事。
    这一问看的是整句还要不要别的，不是在对字符串。
```

开口规则：

```text
没有另一件事：必须开口
  Q1 过 → fulfilled
  Q1 不过 → not_fulfilled
还有另一件事：不要开口把其中一维说成整句办成了或没办成
```

“不要开口”在这张充分性的嘴里叫 inherit。
inherit 是正式出口，不是漏洞。
判定代理的 JSON 仍会给一个总状态；实验里把
“不该因姓名这一维就把整句说成办成了”记成 must_not_fulfilled。

## 3. 边界

看：

1. 用户问句
2. 系统交出来的字段和值
3. 该维已经有的标准

不看：

1. 题型名、混合包角色、样本编号
2. 问句是不是“姓名题”
3. 挖掉交付值之后残句空不空
4. 虚词表
5. 为某个样本加的例外

Q2 的一种够用情况：用户要的事，就是当前这一维的一个值，系统也按这一维交了这个值。
这是够用，不是定义。
定义仍是：整句有没有被这一维说完。

杨杰、王坤林、张伟同一侧，因为值撑得住姓名维。
共展、豆芽没办成，因为值撑不住姓名维，不是因为问句短。
红莲保单、唐诗颖的生存金、只交了产品的“李明的重疾险”：整句还要了别的，这张嘴不要把姓名维说成整句办成了。

## 4. 和对照几何的关系

“值等于整句、且只有一个已授权字段”是 Q2 的一种实例。
它不是架构，也不是判定代理本身。
程序化对照只用来揭穿“换皮规则化”，不能拿它当发版嘴。

def name_standard_reason(value: str, standards) -> tuple[bool, str]:
    text = str(value or "").strip()
    if not _CJK_NAME.fullmatch(text):
        return False, "不是2至4个汉字"
    if text in standards.blacklist:
        return False, "落在该维已有业务黑名单"
    if any(text.endswith(suffix) for suffix in standards.suffixes):
        return False, "带有该维已有业务后缀"
    if text in standards.products:
        return False, "与已有产品名撞车"
    for compound in standards.compounds:
        if text.startswith(compound):
            if len(text) >= len(compound) + 1:
                return True, "2至4个汉字、有已识别复姓、不是产品名/黑名单/业务后缀"

    return False, "没有该维已识别的姓"

def score_llm_rows(rows: list[dict]) -> dict:

        else:
            observe.append(item)
    return {
        "must_ok": must_ok,
        "must_fail": must_fail,
        "observe": observe,
        "must_ok_n": len(must_ok),
        "must_fail_n": len(must_fail),
    }


class MemoryJudgeAgent:

    """In-memory judge agent. Request first, then Q1."""

    def __init__(self, standards):
        self.standards = standards

    def decide(self, query: str, pairs: Optional[list[tuple[str, str]]]) -> dict:
        query = str(query or "").strip()
        if not query:
            return self._inherit("empty_query", query, pairs)
        if pairs is None:
            return self._inherit("pairs_unreadable", query, pairs)

        delivered = [(str(field), str(value)) for field, value in pairs]

        if _CJK_NAME.fullmatch(query):
            return self._judge_dimension(
                query,
                delivered,
                dimension="name",
                field=_NAME_FIELD,
                passed=name_standard_passes(query, self.standards),
            )

        id_hits = [
            (field, value)
            for field, value in delivered
            if field in _ID_FIELDS and value == query
        ]
        if len(delivered) == 1 and id_hits:
            return {
                "status": "fulfilled",
                "reason": "sufficient_id",
                "dimension": "id",
                "field": delivered[0][0],
                "value": delivered[0][1],
            }

        return self._inherit("not_one_complete_dimension", query, delivered)

    def _judge_dimension(self, query, delivered, dimension, field, passed):
        matched = [(f, v) for f, v in delivered if f == field and v == query]
        if not matched:
            return self._inherit(f"{dimension}_not_delivered", query, delivered)
        extras = [(f, v) for f, v in delivered if not (f == field and v == query)]
        if extras:
            return self._inherit("other_delivery_present", query, delivered)
        if passed:
            return {
                "status": "fulfilled",
                "reason": f"sufficient_{dimension}",
                "dimension": dimension,
                "field": field,
                "value": query,
            }
        return {
            "status": "not_fulfilled",
            "reason": f"{dimension}_standard_fail",
            "dimension": dimension,
            "field": field,
            "value": query,
        }

    @staticmethod
    def _inherit(reason, query, pairs):
        return {
            "status": None,
            "reason": reason,
            "dimension": "",
            "field": "",
            "value": query,
            "pair_count": 0 if pairs is None else len(pairs),
        }


def geometric_decide(query: str, pairs: Optional[list[tuple[str, str]]], standards) -> dict:
    """Negative-control shape: live-first, value equals whole request."""
    query = str(query or "").strip()
    if not query or pairs is None or len(pairs) != 1:
        return {"status": None, "reason": "geometric_miss"}
    field, value = pairs[0]
    if value != query:
        return {"status": None, "reason": "geometric_value_not_query", "field": field}
    if field == _NAME_FIELD:
        ok = name_standard_passes(value, standards)
        return {
            "status": "fulfilled" if ok else "not_fulfilled",
            "reason": "geometric_name",
        }
    if field in _ID_FIELDS:
        return {"status": "fulfilled" if value.strip() else "not_fulfilled", "reason": "geometric_id"}
    return {"status": None, "reason": "geometric_field_not_authorized"}


def _pairs(fields, values) -> list[tuple[str, str]]:
    out = []
    for field, value in zip(fields or [], values or []):
        text = str(value).strip()
        name = str(field).strip()
        if name and text:
            out.append((name, text))
    return out


def pairs_from_live(live: dict) -> list[tuple[str, str]]:
    if not isinstance(live, dict):
        return []
    conditions = live.get("conditions")
    if isinstance(conditions, list) and conditions:
        out = []
        for item in conditions:
            if not isinstance(item, dict):
                continue
            field = str(item.get("field") or "").strip()
            value = item.get("value")
            if isinstance(value, (list, tuple)):
                if len(value) != 1:
                    return out
                value = value[0]
            if field and value is not None and not isinstance(value, dict):
                out.append((field, str(value).strip()))
        if out:
            return out
    return _pairs(live.get("fields") or [], live.get("values") or [])

        evidence = list(getattr(result, "evidence", None) or [])
    elif isinstance(payload, dict):
        status = (
            ((payload.get("overall_fulfillment") or {}) if isinstance(payload.get("overall_fulfillment"), dict) else {}).get("status")
            or ((payload.get("summary") or {}) if isinstance(payload.get("summary"), dict) else {}).get("fulfillment_status")
        )
        reason = str(payload.get("reasoning_summary") or "")
        expected_present = payload.get("expected") is not None
        evidence = list(payload.get("evidence") or [])
    else:
        evidence = []
    for item in evidence:
        if isinstance(item, dict) and item.get("source"):
            evidence_source = str(item.get("source"))
            break
    reason_text = reason.strip()
    if reason_text in GEOMETRIC_REASONS or evidence_source == "field_sufficiency":
        source = "geometric"
    else:
        source = "llm"
    return {
        "status": str(status) if status else None,
        "reason": reason[:400],
        "source": source,
        "expected_present": expected_present,
        "evidence_source": evidence_source,
    }


def _exec_module_globals(inst) -> dict:
    """The loaded judge is a freshly exec'd module, often not the imported one."""
    for fn in (
        getattr(type(inst), "reconcile_result", None),
        getattr(type(inst), "pre_judge", None),
        getattr(type(inst), "build_context", None),
    ):
        raw = getattr(fn, "__func__", fn)
        globs = getattr(raw, "__globals__", None)
        if isinstance(globs, dict):
            return globs
    return {}

def run_llm_agent(
    spec,
    cases: list[dict],
    inject_principle: bool,
    workers: int,
    persist=None,
    inject_q1_evidence: bool = False,
) -> list[dict]:
    """Run the real judge object in memory. Official files are not written."""
    from impl.core.pipeline import judge as run_judge

    originals = _install_memory_patches(
        inject_principle=inject_principle,
        inject_q1_evidence=inject_q1_evidence,
    )
    rows = []
    lock = Lock()

    def write_partial():
        if persist is None:
            return
        persist(list(rows))

    try:
        def one(item):
            print(f"[llm] start {item['id']} {item['query']}", flush=True)
            trace = make_trace(
                item["id"],
                item["query"],
                item["pairs"],
                extracted=item.get("extracted"),
            )
            try:
                result = run_judge("client_search", trace, user_intent="")
                parsed = _status_from_result(result)
                if parsed["source"] == "geometric":
                    raise RuntimeError(
                        "geometric mouth still speaking; memory patch missed the loaded judge"
                    )
                row = {
                    "id": item["id"],
                    "query": item["query"],
                    "llm_status": parsed["status"],
                    "llm_reason": parsed["reason"],
                    "source": parsed["source"],
                    "expected_present": parsed["expected_present"],
                    "evidence_source": parsed["evidence_source"],
                    "error": None,
                }
            except Exception as exc:
                row = {
                    "id": item["id"],
                    "query": item["query"],
                    "llm_status": None,
                    "llm_reason": "",
                    "source": None,
                    "expected_present": False,
                    "evidence_source": "",
                    "error": f"{type(exc).__name__}: {exc}",
                    "trace": traceback.format_exc()[-500:],
                }
            print(
                f"[llm] done {row['id']} status={row['llm_status']} source={row.get('source')} err={row['error']}",
                flush=True,
            )
            with lock:
                rows.append(row)
                write_partial()
            return row

        if workers <= 1:
            for item in cases:
                one(item)
        else:
            with ThreadPoolExecutor(max_workers=workers) as pool:
                futures = [pool.submit(one, item) for item in cases]
                for future in as_completed(futures):
                    future.result()
            rows.sort(key=lambda item: item["id"])
    finally:
        _restore_memory_patches(originals)
    return rows

def _scalar_condition_value(value: Any) -> Any:
    """条件值取标量：单元素列表归一为标量；多值/字典（如 RANGE）返回 None。"""
    if isinstance(value, (list, tuple)):
        return value[0] if len(value) == 1 else None
    if isinstance(value, dict):
        return None
    return value


def _operator_justified(
    field: str,
    operator: str,
    manifest_entry: Dict[str, Any],
    equiv_rules: list[Dict[str, Any]],
    value: Any = None,
) -> bool:
    """操作符是否可被下游执行。

    放行条件（确定性 gate，prompt 不得自行放行其他例外）：
    - operator 在字段支持集内；
    - 范围族操作符与支持集中的范围族互容；
    - 显式 semantic_equivalence_rules（equivalent_condition_forms /
      operator_compatibility / equivalent_fields）命中；
    - 单值 MATCH 且字段支持 CONTAINS：仅当条件值（标量或单元素列表）精确等于
      清单枚举值时，才视为后处理可归一为 CONTAINS（不再 blanket 放行）。
    """
    supported = set(manifest_entry.get("operators") or [])
    if operator in supported:
        return True
    value_types = set(manifest_entry.get("value_types") or [])
    if operator == "MATCH" and "CONTAINS" in supported and (
        "enum" in value_types or "list" in value_types or "extract" in value_types
    ):
        scalar = _scalar_condition_value(value)
        if scalar is not None:
            enum_values = {str(item) for item in (manifest_entry.get("enums") or [])}
            if str(scalar) in enum_values:
                return True
    if operator in _RANGE_CAPABLE_OPERATORS and supported & _RANGE_CAPABLE_OPERATORS:
        return True
    for rule in equiv_rules:
        if (
            isinstance(rule, dict)
            and rule.get("field") == field
            and str(rule.get("operator") or "") == operator
        ):
            return True
    return False


def _actual_operator_violations(spec: ProjectSpec, trace: RunTrace) -> list[Dict[str, Any]]:
    manifest = capability_manifest(spec)
    if not isinstance(manifest, dict):
        return []
    equiv_rules = semantic_equivalence_rules(spec)
    output = trace_extracted_output(trace) or {}
    if not isinstance(output, dict):
        return []
    violations: list[Dict[str, Any]] = []
    conditions = output.get("conditions") or output.get("structured_output") or []
    for condition in conditions:
        if not isinstance(condition, dict):
            continue
        field = condition.get("field")
        operator = condition.get("operator")
        entry = manifest.get(field)
        if not field or not operator or not isinstance(entry, dict):
            continue
        if not _operator_justified(str(field), str(operator), entry, equiv_rules, value=condition.get("value")):
            violations.append({
                "field": str(field),
                "operator": str(operator),
                "supported_operators": list(entry.get("operators") or []),
            })
    return violations


def _assessment_uses_operator(
    assessment: FulfillmentAssessment, field: str, operator: str
) -> bool:
    def matches(value: Any) -> bool:
        if isinstance(value, dict):
            if (
                str(value.get("field") or "") == field
                and str(value.get("operator") or "") == operator
            ):
                return True
            return any(matches(item) for item in value.values())
        if isinstance(value, (list, tuple)):
            return any(matches(item) for item in value)
        if isinstance(value, str):
            return field in value and operator in value
        return False

    return matches(assessment.expected_evidence) or matches(assessment.actual_evidence)


def _apply_operator_capability_check(

        "Authority capability/responsibility verification, not by itself proof of "
        "not_fulfilled. A resolved Authority conclusion and the live delivery evidence "
        "determine the assessment."
    )

        "source": "capability_manifest.operator_violation",
        "violations": violations,
        "deferred_conflict_fields": sorted(conflict_fields),
        "rule": violation_rule,

    override_reasons: list[str] = []

        field = violation["field"]
        for assessment in judge_result.fulfillment_assessments or []:
            if not _assessment_uses_operator(

def _operator_justified(
    field: str,
    operator: str,
    manifest_entry: Dict[str, Any],
    equiv_rules: list[Dict[str, Any]],
    value: Any = None,
) -> bool:
    """操作符是否可被下游执行。

    放行条件（确定性 gate，prompt 不得自行放行其他例外）：
    - operator 在字段支持集内；
    - 范围族操作符与支持集中的范围族互容；
    - 显式 semantic_equivalence_rules（equivalent_condition_forms /
      operator_compatibility / equivalent_fields）命中；
    - 单值 MATCH 且字段支持 CONTAINS：仅当条件值（标量或单元素列表）精确等于
      清单枚举值时，才视为后处理可归一为 CONTAINS（不再 blanket 放行）。
    """
    supported = set(manifest_entry.get("operators") or [])
    if operator in supported:
        return True
    value_types = set(manifest_entry.get("value_types") or [])
    if operator == "MATCH" and "CONTAINS" in supported and (
        "enum" in value_types or "list" in value_types or "extract" in value_types
    ):
        scalar = _scalar_condition_value(value)
        if scalar is not None:
            enum_values = {str(item) for item in (manifest_entry.get("enums") or [])}
            if str(scalar) in enum_values:
                return True
    if operator in _RANGE_CAPABLE_OPERATORS and supported & _RANGE_CAPABLE_OPERATORS:
        return True
    for rule in equiv_rules:
        if (
            isinstance(rule, dict)
            and rule.get("field") == field
            and str(rule.get("operator") or "") == operator
        ):
            return True
    return False

def _assessment_uses_operator(

# Fulfillment 三态判定协议（办成了 / 没办成 / 说不清）

> 状态：草稿，待讨论。从业务角度定义 Judge 三态：`fulfilled（办成了）` /
> `not_fulfilled（没办成）` / `not_evaluable（说不清）`。词表沿用 `spec/info-volume.md`，
> 不新增第四态。第一章为长期协议，第二章为现状差异与一次性改造任务。

# 第一章：Spec 标准

## 1. 我们在评什么

三个角色：

- **用户**：使用业务系统的人（mock agent 扮演的角色，即 live request 的提问者），
  不是开发/评测业务系统的人；
- **业务系统**：被评测对象（Live），用户对它说话、它给用户结果；
- **我们**：评测系统（Judge），只看一件事——系统有没有帮用户办成想办的事。

```text
用户期望（BusinessExpectation）
  = 用户用这个产品想办成的事，从用户视角写（例："找到符合要求的客户"）
  ≠ "输出正确的查询结构"（实现视角）

判断分两层：
  第一层：用户要的事办成了没有？
  第二层：手里的材料够不够回答第一层？
```

本协议只评第一层：办成了没有。
「这类事现在是不是产品已经有的功能」见 `spec/alg/product-function.md`，
不并进本协议三态，也不新增第四态。

## 2. 三个状态的定义

### 2.1 办成了（fulfilled）

用户要的事系统给到了，且有实打实的证据。必须同时满足：

1. 属于产品职责范围（职责内）；
2. 材料足够（该查证的查证了，没有悬而未决的依据）；
3. 证据能证明用户要的结果确实拿到了。

### 2.2 没办成（not_fulfilled）

职责内、用户期望明确没达成，且责任在系统。不区分原因：

- 漏条件、加多条件、改错值、条件关系理解错；
- 静默改值、表达不了本可表达的东西；
- 该出结果时一个结果都没出；
- 功能本身未实现，但用户期望已提出。

前提：材料足够；且已排除外部原因（数据库/接口挂了这类不怪系统，见 §4.4）。
理由必须讲清楚，并列为长期优化点——"功能未实现"也是没办成，不降级为说不清。

### 2.3 说不清（not_evaluable）

该给个说法，但材料不够，无法确定办没办成。成因有四类，必须说清"差在哪儿"：

| 差在哪儿 | 什么时候出现 |
|---|---|
| 职责外 | authority 已确认不是产品的职责（例：093 车牌、113 公司名查询） |
| 完全无关 | 用户的事与产品完全不沾边（例：客户搜索产品里问天气）——同属 live boundary 之外 |
| 依据不充分 | authority 真查证过仍 unresolved，分不清"本来就查不了"还是"系统漏了"（例：088 盘客当前状态） |
| 输入坏 | 用户输入本身不可用（例：068 语音损坏），非产品职责也非评测问题 |

职责外是用户确实来要过、产品没这职责；完全无关是根本没沾边。两者都在 live
boundary 之外，都判"说不清"，只是"差在哪儿"要写清楚是哪一种。

三个硬前提（防止变成垃圾桶）：

1. 查证真的激活过：authority 机制真实跑过、有调用记录（"调用记录"= 本次 trace 的
   `authority_tool_call_ids`，或本任务内相同 `decision_question` 的去重命中记录）；"没查证" ≠ "查不了"；
2. 必须写清"差在哪儿"和缺哪份材料（缺料清单）；
3. 是临时态：挂一次性改造限期关闭，不允许成为永久结论。

  要结果（默认） 要拿到具体的客户/名单
  要答复         要"能不能/有没有"的回答（请求文本明确是能力询问）
