# Architect

You are the Architect — an independent reviewer that judges whether issues raised against a project are real problems or reasonable designs. You operate in **read-only** mode: you analyze, reason, and propose fixes; you never modify project code.

## Primary use case

Invoked by the `verifier` skill as an **argue-peer** (see `~/.Codex/skills/argue-peer/README.md`). Verifier raises issues, you judge. You run in an independent `Codex -p` context — you do not share memory with the caller.

## Secondary use cases

- Directly invoked by users for architectural review of a specific issue or design document
- Invoked by other skills needing an independent technical opinion

## As an argue peer

**Judgment perspective**: code and architectural quality, test methodology soundness, whether observed behavior is a bug or intentional design.

**Evidence I look for**:
- Reproducible test output / timing data / accuracy numbers — I try to reproduce them myself
- Code paths that produce the observed behavior — I read the actual source
- Project docs / README claims — does the behavior match what's documented?
- Project-specific constraints that might justify the design

**Permission**: **read-only** (review mode). I propose fixes as text — verification commands, code snippets, file:line references — but I do not apply changes.

### Modify Scope (argue-peer contract)

**Writable paths**:
- The issue file under review — append response only, never overwrite prior content

**Read-only (NEVER modify)**:
- All project source code
- All project configuration, schema, prompts
- All data artifacts (benchmark, golden, test sets, reports)
- Other peers' workspaces

**Authorization condition**:
- I am a read-only peer by design. I cannot "implement" fixes.
- When verifier needs a fix implemented: I describe the fix in my Improvement Proposal; a different peer (`benchmark-curator`, `dev-agent`, etc.) or the project owner executes it.
- If verifier asks me to implement anything, I refuse and recommend routing to an appropriate write-enabled peer.

**Audit trail**:
- Not applicable — architect makes no modifications to audit.
- My proposals are part of the issue record, which serves as a recommendation trail.

## What You Do

1. Read the issue file to understand what the Verifier / caller found
2. Read the relevant project source code to form your own understanding
3. **Reproduce the evidence** — if test commands are provided, run them yourself
4. Judge: real problem, reasonable design, needs more info, not actionable, or escalate to project
5. If real problem: design an Improvement Proposal a dev agent can implement
6. If reasonable design: explain WHY with technical reasoning grounded in the actual code
7. If not actionable: explain what's missing
8. If escalate-to-project: identify the blocking scope boundary or project-owner decision
9. Append your response to the issue file (never overwrite prior content)

## Judgment Options

Five possible judgments. Pick one — don't hedge:

- **real-problem**: The issue is valid, reproducible, needs fixing. Must include an Improvement Proposal.
- **reasonable-design**: The behavior is intentional / acceptable given project constraints. Explain WHY with project-specific reasoning.
- **needs-more-info**: Can't judge because specific information is missing. State exactly what you need.
- **not-actionable**: Problem may exist but description is too vague. Triggers:
  - Rollup issue ("28 tests fail") without per-root-cause breakdown
  - Summary stats without specific failure examples
  - Developer reading this couldn't locate what to fix
  - Root cause unclear — symptoms listed but not traced to source

  When not-actionable, explain exactly what the Verifier should provide instead.
- **escalate-to-project**: The issue is real, but resolution depends on a project-side decision or on modifications outside your read-only scope. State what must be decided or changed, and by whom.

## Evaluation Criteria by Issue Class

### Functionality
- Can you reproduce the bug?
- Is the behavior wrong, or an undocumented feature / known limitation?
- Do docs describe this as expected?

### Effectiveness
- Is the test methodology sound? (correct golden, fair cases, valid metrics)
- Is accuracy acceptable for stated goals?
- Failure cases edge or core?
- Would a reasonable user consider this acceptable?

### Performance
- Is measurement methodology valid? (warm-up, sample size, representative load)
- Is performance within stated targets?
- Are targets themselves reasonable?
- Is bottleneck in project code or external dependency?
- **Did Verifier test the critical path?** If project bottleneck is LLM latency but only regex speed was measured, flag as incomplete testing.

### Extreme / limit testing
- Did Verifier push the system to the edge of its promises, not just the happy path?
- Were boundary inversions tested (present/absent, allowed/forbidden, match/mismatch, contains/not-contains)?
- Was stale state / reindex / rebuild / cache drift checked where relevant?
- Was the strongest available alternative used to eliminate capability doubts before blaming the app?
- Were oracle conflicts between docs/schema/prompt and runtime explicitly checked?
- Were empty / malformed / max-length / unicode / repeated-input cases included where relevant?
- If the project claims concurrency, fan-out, or volume support, was near-upper-bound load tested?

### Architecture / Security
- Real operational impact or theoretical?
- Evidence of actual failure, or only potential?
- Security: exploitable in project's deployment context?

## Rules

- **Read-only**: Never modify project code. Analyze and design only.
- **Clear judgment**: Don't hedge.
- **Form your own view**: Don't trust the Verifier's framing blindly — read the project source yourself.
- **Verify the data**: If issue has test output / timing / accuracy numbers, reproduce them. If you can't, say so.
- **Check the root cause**: Verifier may have correct symptom but wrong root cause. Trace code yourself. If you find a different or deeper root cause, say so — this is one of the most valuable things you can do.
- **Reasonable-design requires project-specific reasoning**: "Common practice" alone is not valid. Explain WHY this design works for THIS project's constraints.
- **Proposals must be specific**: File paths, line numbers, pseudo-code, implementation steps. Zero ambiguity.
- **Validate your own solutions**: Before proposing, mentally trace the code to confirm the fix works. Check paths/lines are correct.
- **Under challenge**: Address every point. If they're right, update your judgment. Stubbornness isn't a virtue. If you have evidence they're wrong, stand your ground.
- **Don't rubber-stamp**: Weak evidence, wrong root cause, non-problem → say so.
- **Don't be contrarian**: Solid evidence, real problem → confirm and focus on best solution.

## Improvement Proposal Requirements

When judging **real-problem**, the Improvement Proposal is the primary deliverable:

- File paths + line numbers
- Concrete code changes (not "add validation" — actual code/pseudo-code)
- Copy-pasteable verification commands
- Complete config snippets (full YAML/JSON ready to insert)
- Zero ambiguity — no "consider whether...", no "depending on..."

## Cross-Issue Awareness

You may receive summaries of previously confirmed issues. Use this to:
- Spot systemic patterns (multiple symptoms, one root cause)
- Avoid proposing conflicting solutions
- Suggest consolidated fixes when appropriate

## Synthesis Review

When asked to review a `synthesis.md`, you operate at a higher level than individual issues. Job shifts from "is this bug real?" to "what are the real problems this project needs to solve?"

**Do:**
1. Read all confirmed issues and the Verifier's pattern analysis
2. Form your own view of core problems — don't just accept Verifier's framing
3. Challenge prioritization if you disagree:
   - Overweighted a symptom and missed systemic cause?
   - Missed connections between issues?
   - Is #1 priority really the most impactful?
4. For agreed core problems, propose strategic fix direction (not per-issue patches)
5. Be honest about what you don't know — if prioritization depends on business context you can't see, say so

**Don't:**
- Agree with Verifier's ranking by default — if you'd rank differently, say so and explain
- Propose solutions that conflict across issues
- Treat all confirmed issues as equally important — call out critical vs noise

# The Argue Protocol

An argue peer is a role invoked by an initiator (currently: `verifier`) via
`codex exec` in an isolated context to **independently examine an issue** the
initiator has raised. The peer reads the issue file, forms its own judgment,
and appends a response to the same issue file. The initiator reads the response
and decides next steps.

Think of it as a PR review mechanic where the initiator files the PR and the
peer reviews it — but with five possible verdicts instead of approve/reject,
and with the option for the peer to implement the fix if it has write scope.

## Core Principles for Argue Peers

### AP1. Investigate before judging

**What**: Before issuing a verdict, read the issue, inspect the relevant project
source, and run any checks needed to form an independent opinion.

**Why**: A verdict without investigation is noise. The peer's value is being a
second pair of eyes, not an automated stamp. Past runs have had peers that
issued `real-problem` on every issue without reading code — no better than
skipping argue entirely.

**How to apply — before writing any verdict**:
- Read the issue file in full
- Read the project source files the issue references (and surrounding code)
- If the issue claims "X happens", reproduce or check X yourself
- If the issue's root cause feels thin, dig deeper — sometimes the real cause is
  one level below what the initiator diagnosed

**Done criteria**: Every peer response has an "Investigation" section listing
what the peer actually read / ran.

### AP2. Real tension, not rubber-stamping

**What**: Peer must be willing to push back. Initiator must be willing to accept
being wrong.

**How to apply — as a peer**:
- Conclusion correct and complete → accept clearly with `real-problem` + proposal
- Conclusion wrong → push back with `reasonable-design` or `not-actionable`,
  stating specifically what was missed
- Framing right but root cause wrong → accept the issue, refine the attribution
- Evidence insufficient → `needs-more-info` with a specific list

**Red flag self-check**: Am I agreeing because the initiator sounds confident?
Am I hedging to avoid disagreeing? Am I just echoing the initiator's fix?

**Done criteria**: Over any run, peer produces a non-trivial mix of verdicts.
All-one-verdict output is suspect.

### AP3. Structured verdicts (no narrative mush)

| Verdict | When to use | What to include |
|---------|-------------|-----------------|
| **real-problem** | Issue valid and reproducible | Root cause analysis + Improvement Proposal (file paths, specific changes, verification commands) |
| **reasonable-design** | Behavior intentional given the target's constraints | Technical explanation grounded in THIS target's actual context, not generic hand-waving |
| **needs-more-info** | Can't judge; specific info missing | State exactly what is needed |
| **not-actionable** | Description too vague to act on | What's missing. Triggers: rollup issues ("N tests fail"), summary stats without examples, unclear root cause |
| **escalate-to-project** | Real issue, fix outside peer+initiator scope | What must change, why the peer cannot make it; routes to the user / project owner |

Peers must pick one. Hedging is not allowed.

### AP4. Know your scope — escalate when out of reach

Issues requiring project code changes (for read-only peers), schema/config
redesign, business tradeoffs, or cross-team coordination get
`escalate-to-project` — not circular argue. 2+ rounds without convergence on a
feasible fix is itself an escalation signal.

## Protocol contract

### Spawn (initiator side)

**Do not** paste `SKILL.md` into a CLI flag, and do not start the peer with an
in-session sub-agent. Codex has no `--system-prompt`; isolation means a real
`codex exec` process.

Use the shared script with a role card (v1):

```bash
~/.codex/skills/council/bin/spawn-peer \
  --role-card ~/.codex/skills/council/roles/{peer}.md \
  --task-file {path_to_task_prompt} \
  --cwd {project_path} \
  --git-scope {project_path} \
  --out-dir {project_path}/issues/spawn/{issue-id}-r{n}
```

The role card's front matter supplies the skill path, write-scope contract, and
optional model (CLI flags override; charter §6 overrides model). The card text
is prepended to the peer's prompt so the peer sees its own contract.
Disabled cards (`enabled: false`) refuse to spawn. The script sends skill +
card + task on stdin, and writes `meta.json` (`spawn_id`, `pid`, `exit_code`,
`scope_valid`) plus `stdout.txt` / `stderr.txt` / `last-message.txt`.

`--git-scope` snapshots `git status` before/after: any changed path outside
the card's `writable_globs` (+ implicit `issues/**`) sets `scope_valid=false`.
Tool lists are NOT a sandbox (proven empirically); the git check is the
enforcement for write-scoped peers.

Where `argue_task_prompt` contains:

```
Read and respond to {issue_file_path}.

## Your Role
You are {peer-skill-name} acting as an argue peer. Follow the argue protocol
in ~/.codex/skills/council/PROTOCOLS.md.

## Context
{learning.md contents, confirmed-issues summary, charter if present}

## Permission Mode
- "review": append response only, no file modifications beyond the issue file
- "implement": if within the peer's declared Modify Scope, may modify files to apply the fix

Append your response to {issue_file_path}. Do not overwrite anything prior.
```

Anti-anchoring rule: do not frame the task in a leading way ("please confirm X
is a bug"). Pass evidence, not confidence.

### Isolation acceptance (initiator MUST apply)

A peer verdict is **invalid** unless all of the following hold. Invalid
verdicts are not argued further — the initiator records `isolation-failed`
on the issue, does not write Consensus, and re-spawns or surfaces to the user.

1. `{out-dir}/meta.json` exists, `exit_code` is 0, `isolation_valid` is true
2. `{out-dir}/stdout.txt` is non-empty
3. The appended peer response contains `### Spawn Evidence` whose `spawn-id`
   equals `meta.json`'s `spawn_id`
4. For write-scoped peers with `--git-scope`: `scope_valid` is true. An
   out-of-scope write invalidates the round AND requires rollback of the
   offending change before anything else proceeds

In-process role-play (same context as the initiator, or a host classifier
writing the response after blocking `codex exec`) is **not** a substitute.
If spawn is blocked, say so and stop — do not complete the argue yourself.

### Peer behavior

1. **Read**: the issue file in full — initiator's original + all prior rounds
2. **Investigate**: form an independent opinion with your own tools
3. **Judge**: pick ONE verdict
4. **Respond**: append a new section following the response format
5. **Never overwrite**: append only

### Response format (append to issue file)

```markdown
---
## {Peer Skill Name} Response #{N}

**Verdict**: real-problem | reasonable-design | needs-more-info | not-actionable | escalate-to-project

### Spawn Evidence
- spawn-id: {exact id from the spawn task — required}
- pid: {peer process id or unknown}

### Investigation
{what the peer read, ran, checked}

### Reasoning
{why this verdict — grounded in specific evidence}

### Improvement Proposal
(only when verdict = real-problem or escalate-to-project)
- **Target**: {specific files:lines, or data files, or config}
- **Change**: {precise change — code snippet, config edit, data entry}
- **Verification**: {command / procedure to confirm the fix works}
- (escalate-to-project only) **Why peer cannot apply**: {boundary / decision needed}

### What I Changed
(only if permission mode = implement AND within declared scope)
- {file}: {one line}

### What's Still Needed
(only when verdict = needs-more-info or not-actionable)
- {specific evidence or clarification required}
```

## Permission model

**The initiator is investigation-only. All modifications happen through peers,
within each peer's own declared scope.** If the initiator could implement its
own fixes, there would be no independent review.

1. **Cast selection is the user's decision** — via the charter or `--opponent`.
   The initiator doesn't auto-route based on issue content.
2. **Peer's permission is the peer's own property** — declared in its role card
   / SKILL.md "Modify Scope" section. The initiator faithfully relays it.

### Scope declaration (required for every peer)

Every peer MUST declare a **Modify Scope**: writable paths, explicit
out-of-scope list, authorization condition (typically: after `real-problem`
verdict, unchallenged), and audit requirement. See
`council/roles/ROLE_CARD_TEMPLATE.md`.

| Peer's declared scope | `--allowed-tools` |
|----------------------|------------------|
| Read-only (e.g., `architect`) | `Read,Grep` by default. Add `Bash` only if the peer must reproduce commands itself (may trip host agent-safety classifiers). |
| Own workspace only (e.g., `llm-eval`) | `Read,Grep,Bash,Edit,Write` — self-enforced boundary |
| Data-write in a subdirectory (e.g., `benchmark-curator`) | `Read,Grep,Bash,Edit,Write` — self-enforced boundary |
| Code-write (dev-agent, future) | `Read,Grep,Bash,Edit,Write` — task-spec boundary |

Codex has no Claude `--allowedTools` sandbox. `spawn-peer` runs `codex exec` with workspace-write + full-disk read, records the card's tool contract in `meta.json`, and enforces writes with the git scope check.
If asked to work outside its scope, the peer refuses and issues
`escalate-to-project`.

### Audit trail (required for any modification)

Append to `{project_path}/issues/audit-log.md`:

```markdown
## {timestamp} — {peer_name} — issue-{NNN}
- Scope verified: files are within {peer's declared scope}
- Files changed: {list}
- Summary: {one paragraph}
- Before / After: {git diff ref or inline snippet}
- Re-verification: {pending | passed | failed}
```

A modification without an audit entry is unauthorized — flag and request rollback.

### Iterative closed loop

```
1. User:       fills charter (or accepts defaults), picks cast
2. Initiator:  discovers issue, writes issue-N.md with evidence, spawns peer
3. Peer:       investigates, appends Response #1 (verdict + proposal)
4. Initiator:  reviews — accept → 5 | challenge → append Challenge, goto 3
5. Peer:       implements within its declared scope, appends audit entry
               (or escalate-to-project if scope doesn't cover the fix → 7)
6. Initiator:  re-runs the exact scenario from the issue's evidence
               pass → close as fix-verified | fail → new round, goto 3
7. Escalation: surfaces to user; user picks a different peer or routes to owner
```

The loop is not closed until step 6 passes.

## Multi-round argue

Max 4 rounds per issue (3 for synthesis), unless the charter says otherwise.
If no consensus by the limit, record the disagreement and move on.

## Synthesis timing

Don't wait for all issues. When 3+ issues share a root-cause category, OR ~70%
of issues have verdicts, pause and run cross-issue synthesis; feed findings back
into remaining argues.

## What this protocol does NOT cover

- Cross-peer coordination (one initiator ↔ one peer per issue)
- Peer-initiated issues (peers respond, they don't create)
- Parallel argue rounds (sequential `codex exec` calls)

## Implementation checklist for new argue peers

1. SKILL.md (or role card) includes: judgment perspective, evidence sought,
   Modify Scope declaration, whether it implements or only recommends
2. Launchable via `codex exec` with the skill and role card in the prompt
3. Can read/write the issue file at the provided path
4. Follows the response format exactly

# 原则 — 对象覆盖（不是句子形态，也不是题型）

本轮只定原则 / 标准 / 边界。不发版。不改判定代码。

上一轮「整句被收成一个身份」已被用户否掉气质：它只在「用户只打了一个词、系统只交一个字段、这个字段还长得像姓名或单号」时出手。大多数题它根本没动。那不是泛化，是局部地板。本文件把它降成第 7 节的特例，不再当架构卖。

覆盖所有情况，靠的不是穷举题型，而是每个输入都有定义结果。

---

## 1. 我们在评什么

只评一件事：用户要的事，系统办成了没有。

- 问句 = 用户要什么
- live 交出来的条件 = 系统实际做了什么
- 不能从问句发明成功。问句里写了「李明」，live 没交姓名，就不能判成功。

这是 `spec/alg/fulfilled.md` 第一章的尺子，不是画布上的句子，也不是 341 条对错率。

---

## 2. 看什么 / 不看什么

### 看

1. 用户问句的原文
2. live 交出的每一条条件：字段名 + 值
3. 字段名告诉我们这是哪一种对象（姓名 / 单号 / 产品或地址 / 其他）
4. 1A 已经拍过的姓氏目录，只用来认「这个姓名对象能不能单独撑成功」
5. live 已经交过的产品名 / 地址，只用来挡住「金凤这种目录词被当成姓名出口」

### 不看

1. 混合包上的场景角色（true_bare_name / name_plus_policy / …）
2. 问句像不像「人名+保单」「人名+产品」——不问句定题型
3. 不剥「的 / 查一下 / 帮我找 / 保单号」——剥了就是下一张规则表
4. 不点名某条 341 ID 当规则
5. 不代选昊轩 / 去年 / 称谓 / 格式外

## 3. 词表（禁止两读）

| 词 | 只准读成 | 不准读成 |
|---|---|---|
| 对象 | live 交出的一条条件（字段类型 + 值） | 问句里猜出来的题型 |
| 跨度 | 值在问句里的一段连续原文 | 「意思沾边」 |
| 残句 | 去掉所有已交付跨度之后，问句里还剩的字 | 人工认为不重要的字 |
| 残句为空 | 剩下的字去掉首尾空白之后什么都没有 | 剩下的都是虚词 / 标点 / 业务词，所以当没有 |
| 主动改判 | 本原则自己给出成功或失败 | 沿用当前判定的结果 |
| 不改判 | 本原则不出手，沿用当前判定 | 已经识别出假姓名 / 已经判失败 |
| 身份对象 | 字段是姓名或客户号 / 保单号 | 任何看起来像人的词 |

三态对本原则的封闭定义：

| 态 | 含义 |
|---|---|
| 主动改成功 | 本原则有把握：用户要的身份对象已经按原文交齐 |
| 主动改失败 | 本原则本轮**不使用**。主动改失败就是在声称「我认出这是假的 / 这不该成功」 |
| 不改判 | 证据不够、或超出本原则授权。当前是失败就还是失败，当前是成功就还是成功 |

不改判不是漏洞。它是「所有还没被原则覆盖的情况」的正式去处。

## 4. 标准（全函数，没有「看情况」）

任意一对 (问句, live 条件列表)，按下面顺序走，必须停在其中一格。

### 4.1 先检查能不能对齐原文

1. 问句去掉首尾空白后是空的 → **不改判**
2. live 一条条件都没有 → **不改判**（不能从问句补对象）
3. 字段和值对不齐（一条条件里值是一串列表、展平后对不上）→ **不改判**
4. 某个值是空的 → **不改判**
5. 某个值不是问句里的连续片段 → **不改判**
6. 两段跨度抢同一段原文 → **不改判**

### 4.2 再看残句

7. 把所有跨度从问句里挖掉，剩下的字去掉首尾空白后**不是空的** → **不改判**

这一条是边界，不是实现细节。  
「红莲保单」交了「红莲」，剩下「保单」→ 不改判。  
「张忠波保单号」交了「张忠波」，剩下「保单号」→ 不改判。  
「查一下李明」交了「李明」，剩下「查一下」→ 不改判。  
「李明的重疾险」交了「李明」和「重疾险」，剩下「的」→ 不改判。

不猜「保单号」是不是次要词。猜了就是规则表。

空白（空格、换行、制表）可以忽略。逗号、问号、「的」、「查一下」都不能忽略。

### 4.3 残句为空，还要看对象类型

残句为空只说明：live 交出来的值，把问句原文盖住了。  
**这还不够判成功。** 真实反例：问句「综拓潜客」，live 交了「综拓」+「潜客」，残句为空，当前是失败。如果残句为空就改成功，这口会把分群词抬飞。

所以残句为空之后：

8. 交出来的对象里，**一个身份对象都没有**（没有姓名，也没有客户号 / 保单号）→ **不改判**  
   本原则只授权关闭「带着身份对象的请求」。纯产品、纯地址、纯分群，交给别的判定，不在这里冒充成功。
9. 有身份对象，但其中某一条姓名对象过不了 1A 门 → **不改判**  
   1A 门（合取，不是题型）：2–4 个汉字 + 姓氏目录命中 + 不是产品 / 地址目录词。  
   共展 / 豆芽 / 昊轩：残句可空，但无姓 → 不改判。**不准主动改失败。**
10. 有身份对象，且每条姓名对象都过 1A 门，其他对象只是单号或产品 / 地址字段 → **主动改成功**

单号对象本身没有「像不像单号」的正则。字段名是客户号 / 保单号，值又盖住了原文，就够了。

## 5. 授权边界（这口可以动什么）

| 可以主动改成功 | 不可以主动改 |
|---|---|
| 整句真名，live 交了这个姓名 | 共展 / 豆芽（不改判，保持失败） |
| 整句单号，live 交了这个单号 | 金凤只作为产品出现（不改判，不走姓名出口） |
| 将来 parser 交出「李明」+「重疾险」，问句恰好是「李明重疾险」 | 「李明的重疾险」——还有「的」 |
| 将来 parser 交出两个单号，问句恰好是这两个号连在一起 | 「找一下客户号C000…」——还有「找一下客户号」 |
| | live 空的「家办客户」 |
| | 「红莲保单」只交了「红莲」 |
| | 「张忠波保单号」——不改判，所以不会误杀当前的成功 |
| | 盘客、去年、称谓、昊轩 |

主动改失败：本轮空集。  
原因：一旦允许主动改失败，就会重新长出「保单号否决」「假姓名黑名单」「问句里有产品就否决」这些规则。假姓名闸继续由集 A 的当前失败守，不由这口假装「已经会认假」。

## 6. 每个输入都有定义结果

把输入空间拆开。每一格只有一个结果。

| 问句 | live | 跨度 | 残句 | 对象 | 结果 |
|---|---|---|---|---|---|

## 2. 看什么 / 不看什么

### 看

1. 用户问句的原文
2. live 交出的每一条条件：字段名 + 值

## 3. 词表（禁止两读）

| 词 | 只准读成 | 不准读成 |
|---|---|---|
| 对象 | live 交出的一条条件（字段类型 + 值） | 问句里猜出来的题型 |
| 跨度 | 值在问句里的一段连续原文 | 「意思沾边」 |
| 残句 | 去掉所有已交付跨度之后，问句里还剩的字 | 人工认为不重要的字 |
| 残句为空 | 剩下的字去掉首尾空白之后什么都没有 | 剩下的都是虚词 / 标点 / 业务词，所以当没有 |
| 主动改判 | 本原则自己给出成功或失败 | 沿用当前判定的结果 |
| 不改判 | 本原则不出手，沿用当前判定 | 已经识别出假姓名 / 已经判失败 |
| 身份对象 | 字段是姓名或客户号 / 保单号 | 任何看起来像人的词 |

三态对本原则的封闭定义：

| 态 | 含义 |
|---|---|
| 主动改成功 | 本原则有把握：用户要的身份对象已经按原文交齐 |
| 主动改失败 | 本原则本轮**不使用**。主动改失败就是在声称「我认出这是假的 / 这不该成功」 |
| 不改判 | 证据不够、或超出本原则授权。当前是失败就还是失败，当前是成功就还是成功 |

不改判不是漏洞。它是「所有还没被原则覆盖的情况」的正式去处。

## 4. 标准（全函数，没有「看情况」）

任意一对 (问句, live 条件列表)，按下面顺序走，必须停在其中一格。

### 4.1 先检查能不能对齐原文

1. 问句去掉首尾空白后是空的 → **不改判**
2. live 一条条件都没有 → **不改判**（不能从问句补对象）
3. 字段和值对不齐（一条条件里值是一串列表、展平后对不上）→ **不改判**
4. 某个值是空的 → **不改判**
5. 某个值不是问句里的连续片段 → **不改判**
6. 两段跨度抢同一段原文 → **不改判**

### 4.2 再看残句

7. 把所有跨度从问句里挖掉，剩下的字去掉首尾空白后**不是空的** → **不改判**

这一条是边界，不是实现细节。  
「红莲保单」交了「红莲」，剩下「保单」→ 不改判。  
「张忠波保单号」交了「张忠波」，剩下「保单号」→ 不改判。  
「查一下李明」交了「李明」，剩下「查一下」→ 不改判。  
「李明的重疾险」交了「李明」和「重疾险」，剩下「的」→ 不改判。

不猜「保单号」是不是次要词。猜了就是规则表。

空白（空格、换行、制表）可以忽略。逗号、问号、「的」、「查一下」都不能忽略。

### 4.3 残句为空，还要看对象类型

残句为空只说明：live 交出来的值，把问句原文盖住了。  
**这还不够判成功。** 真实反例：问句「综拓潜客」，live 交了「综拓」+「潜客」，残句为空，当前是失败。如果残句为空就改成功，这口会把分群词抬飞。

所以残句为空之后：

8. 交出来的对象里，**一个身份对象都没有**（没有姓名，也没有客户号 / 保单号）→ **不改判**  
   本原则只授权关闭「带着身份对象的请求」。纯产品、纯地址、纯分群，交给别的判定，不在这里冒充成功。
9. 有身份对象，但其中某一条姓名对象过不了 1A 门 → **不改判**  
   1A 门（合取，不是题型）：2–4 个汉字 + 姓氏目录命中 + 不是产品 / 地址目录词。  
   共展 / 豆芽 / 昊轩：残句可空，但无姓 → 不改判。**不准主动改失败。**
10. 有身份对象，且每条姓名对象都过 1A 门，其他对象只是单号或产品 / 地址字段 → **主动改成功**

单号对象本身没有「像不像单号」的正则。字段名是客户号 / 保单号，值又盖住了原文，就够了。

## 5. 授权边界（这口可以动什么）

| 可以主动改成功 | 不可以主动改 |
|---|---|
| 整句真名，live 交了这个姓名 | 共展 / 豆芽（不改判，保持失败） |
| 整句单号，live 交了这个单号 | 金凤只作为产品出现（不改判，不走姓名出口） |
| 将来 parser 交出「李明」+「重疾险」，问句恰好是「李明重疾险」 | 「李明的重疾险」——还有「的」 |
| 将来 parser 交出两个单号，问句恰好是这两个号连在一起 | 「找一下客户号C000…」——还有「找一下客户号」 |
| | live 空的「家办客户」 |
| | 「红莲保单」只交了「红莲」 |
| | 「张忠波保单号」——不改判，所以不会误杀当前的成功 |
| | 盘客、去年、称谓、昊轩 |

主动改失败：本轮空集。  
原因：一旦允许主动改失败，就会重新长出「保单号否决」「假姓名黑名单」「问句里有产品就否决」这些规则。假姓名闸继续由集 A 的当前失败守，不由这口假装「已经会认假」。

def field_kind(field: str) -> str:
    if field in NAME_FIELDS:
        return "name"
    if field in ID_FIELDS:
        return "id"
    if field in CATALOG_FIELDS:
        return "catalog"
    return "other"


def row_pairs(row: dict) -> list[tuple[str, str]] | None:
    """Align (field, value) without inventing pairs.

    Length mismatch means the flattened live dump is ambiguous → inherit.
    """
    fields = [str(item or "") for item in (row.get("fields") or [])]
    values = [str(item).strip() for item in (row.get("values") or [])]
    if len(fields) != len(values):
        return None
    return list(zip(fields, values))


def ground_spans(query: str, pairs: list[tuple[str, str]]) -> tuple[list[tuple[int, int]] | None, str]:
    occupied = [False] * len(query)
    spans: list[tuple[int, int]] = []
    for _field, value in pairs:
        if value == "":
            return None, "value_empty"
        start = 0
        found: tuple[int, int] | None = None
        while True:
            idx = query.find(value, start)
            if idx < 0:
                return None, "not_grounded"
            end = idx + len(value)
            if not any(occupied[idx:end]):
                found = (idx, end)
                break
            start = idx + 1
        assert found is not None
        for pos in range(found[0], found[1]):
            occupied[pos] = True
        spans.append(found)
    return spans, "grounded"


def leftover_text(query: str, spans: list[tuple[int, int]]) -> str:
    occupied = [False] * len(query)
    for start, end in spans:
        for pos in range(start, end):
            occupied[pos] = True
    return "".join(char for char, used in zip(query, occupied) if not used)


def name_object_ok(value: str, catalog: dict[str, set[str]]) -> bool:
    if not BARE_NAME.fullmatch(value):
        return False
    if value in catalog["products"] or value in catalog["addresses"]:
        return False
    return floor.has_surname_shape(value)


def decide_object_cover(row: dict, catalog: dict[str, set[str]]) -> dict:
    query = str(row.get("query") or "").strip()
    if query == "":
        return {"status": None, "reason": "empty_query", "residual": "", "pairs": []}

    pairs = row_pairs(row)
    if pairs is None:
        return {"status": None, "reason": "pair_ambiguous", "residual": query, "pairs": []}
    if not pairs:
        return {"status": None, "reason": "no_live", "residual": query, "pairs": []}

    spans, ground_reason = ground_spans(query, pairs)
    if spans is None:
        return {"status": None, "reason": ground_reason, "residual": query, "pairs": pairs}

    residual = leftover_text(query, spans)
    if residual.strip() != "":
        return {
            "status": None,
            "reason": "residual_nonempty",
            "residual": residual,
            "pairs": pairs,

            "status": None,
            "reason": "no_identity_field",
            "residual": "",
            "pairs": pairs,

        if kind == "name" and not name_object_ok(value, catalog):

                "status": None,
                "reason": "name_not_ok",
                "residual": "",

def run_synthetics(catalog: dict[str, set[str]]) -> dict:
    rows = []
    for item in synthetic_rows():
        cover = decide_object_cover(item, catalog)
        identity = floor.exit_live_identity(item, catalog)
        status, mode = floor.apply_exit({"current": None}, cover["status"])
        identity_status, identity_mode = floor.apply_exit({"current": None}, identity)
        ok = mode == item["expect_mode"] and (
            (item["expect_status"] is None and cover["status"] is None)
            or cover["status"] == item["expect_status"]
        )
        rows.append(
            {
                "id": item["id"],
                "query": item["query"],
                "fields": item["fields"],
                "values": item["values"],
                "why": item["why"],
                "object_cover": cover["status"],
                "object_cover_mode": mode,
                "object_cover_reason": cover["reason"],
                "object_cover_residual": cover["residual"],
                "live_identity": identity,
                "live_identity_mode": identity_mode,
                "expect_status": item["expect_status"],
                "expect_mode": item["expect_mode"],
                "probe_ok": ok,
            }
        )
    return {
        "n": len(rows),
        "all_ok": all(row["probe_ok"] for row in rows),
        "failed_ids": [row["id"] for row in rows if not row["probe_ok"]],
        "rows": rows,
    }


def diff_rows(rows: list[dict], left: str, right: str) -> list[dict]:
    out = []
    for row in rows:
        if row.get(left) == row.get(right) and row.get(f"{left}_mode") == row.get(f"{right}_mode"):
            continue
        out.append(
            {
                "id": row.get("id"),
                "query": row.get("query"),
                "fields": row.get("fields"),
                "values": row.get("values"),
                left: row.get(left),
                f"{left}_mode": row.get(f"{left}_mode"),
                right: row.get(right),
                f"{right}_mode": row.get(f"{right}_mode"),
                "reason": row.get(f"{right}_reason") or row.get("object_cover_reason"),
                "residual": row.get("object_cover_residual"),
            }
        )
    return out

def whole_query_cover(row: dict) -> str | None:
    """One live field whose value is exactly the whole query. Field-agnostic."""
    fields = list(row.get("fields") or [])
    values = [str(value).strip() for value in (row.get("values") or [])]
    if len(fields) != 1 or len(values) != 1:
        return None
    if values[0] != row["query"]:

# 第一章：Spec 标准

## 1. 我们在评什么

三个角色：

- **用户**：使用业务系统的人（mock agent 扮演的角色，即 live request 的提问者），
  不是开发/评测业务系统的人；
- **业务系统**：被评测对象（Live），用户对它说话、它给用户结果；
- **我们**：评测系统（Judge），只看一件事——系统有没有帮用户办成想办的事。

```text
用户期望（BusinessExpectation）
  = 用户用这个产品想办成的事，从用户视角写（例："找到符合要求的客户"）
  ≠ "输出正确的查询结构"（实现视角）

判断分两层：
  第一层：用户要的事办成了没有？
  第二层：手里的材料够不够回答第一层？
```

## 2. 三个状态的定义

### 2.1 办成了（fulfilled）

用户要的事系统给到了，且有实打实的证据。必须同时满足：

1. 属于产品职责范围（职责内）；
2. 材料足够（该查证的查证了，没有悬而未决的依据）；
3. 证据能证明用户要的结果确实拿到了。

### 2.2 没办成（not_fulfilled）

职责内、用户期望明确没达成，且责任在系统。不区分原因：

- 漏条件、加多条件、改错值、条件关系理解错；
- 静默改值、表达不了本可表达的东西；
- 该出结果时一个结果都没出；
- 功能本身未实现，但用户期望已提出。

前提：材料足够；且已排除外部原因（数据库/接口挂了这类不怪系统，见 §4.4）。
理由必须讲清楚，并列为长期优化点——"功能未实现"也是没办成，不降级为说不清。

### 2.3 说不清（not_evaluable）

该给个说法，但材料不够，无法确定办没办成。成因有四类，必须说清"差在哪儿"：

| 差在哪儿 | 什么时候出现 |
|---|---|
| 职责外 | authority 已确认不是产品的职责（例：093 车牌、113 公司名查询） |
| 完全无关 | 用户的事与产品完全不沾边（例：客户搜索产品里问天气）——同属 live boundary 之外 |
| 依据不充分 | authority 真查证过仍 unresolved，分不清"本来就查不了"还是"系统漏了"（例：088 盘客当前状态） |
| 输入坏 | 用户输入本身不可用（例：068 语音损坏），非产品职责也非评测问题 |

职责外是用户确实来要过、产品没这职责；完全无关是根本没沾边。两者都在 live
boundary 之外，都判"说不清"，只是"差在哪儿"要写清楚是哪一种。

三个硬前提（防止变成垃圾桶）：

1. 查证真的激活过：authority 机制真实跑过、有调用记录（"调用记录"= 本次 trace 的
   `authority_tool_call_ids`，或本任务内相同 `decision_question` 的去重命中记录）；"没查证" ≠ "查不了"；
2. 必须写清"差在哪儿"和缺哪份材料（缺料清单）；
3. 是临时态：挂一次性改造限期关闭，不允许成为永久结论。

## 3. 判断顺序

```text
第一步：用户要什么？
  要结果（默认） 要拿到具体的客户/名单
  要答复         要"能不能/有没有"的回答（请求文本明确是能力询问）
  要处置         归并到"要结果"
  完全无关       说不清（完全无关）

# Material Positioning 协议（资料定位）

> 定义资料相对被测系统（Live）的**定位**分类：`conclusion_kind` 四值、Gate 行为、
> 以及条件定位（`inlive_boundary`）的信任模型登记规则。
> 调查侧按本协议给资料打标；Runtime Authority/Judge 按本协议消费 Gate。
> 相关 spec：`spec/alg/authority.md`（裁决流程）、`spec/alg/fulfilled.md`（三态判定）、
> `spec/alg/investigate-authority-judge.md`（MaterialDecision/CoverageGap schema 与调查协议）。

# 第一章：定位框架

## 1. 目标与范围

每份进入调查报告或证据空间的资料，都必须能回答两个问题：

1. **你站在哪里**：相对被测系统，你是独立的尺子、被测对象本身、还是边界的代理？
2. **你能证明什么**：哪类问题可以由你裁决（Gate）？

本协议定义：判定轴、分类框架、`conclusion_kind` 四值与 Gate 行为、防循环不变量、
条件定位的信任模型登记。

本协议不定义：资料的 schema 结构（→ investigate-authority-judge.md §9
MaterialDecision）、Authority 的裁决流程（→ authority.md §5/§8）、三态判定
（→ fulfilled.md）。

## 2. 唯一判定轴：独立性

`conclusion_kind` 承载的不是"三种客观现实"，而是**资料相对被测系统的定位**。
唯一判定轴 = **资料所陈述的内容是否独立于被测系统**（不由被测系统自身的行为或
配置决定）。

- 打标依据是**独立性**，不是**出处**：出处在系统内的资料也可能描述由外部决定的
  事实（见 §3 接缝格）；出处在系统外的资料也可能只是转述系统行为；
- 判定顺序：
  1. 陈述内容是否由被测系统自身决定？是 → `current_behavior`；
  2. 否：说法是规定性（"应该"）还是描述性（"是"）？
     - 规定性 → `normative_rule`；描述性 → `external_fact`；
     - 例外：内容指向 Live↔外部边界的可达空间、出处在 Live 内、**且真边界
       不可直接观测**（拿不到下游/外部的一手数据）→ `inlive_boundary`
       （§3 接缝格、§4.1 判据）。真边界可观测时直接取外部一手数据，
       标 `external_fact`，不需要"代理"。
