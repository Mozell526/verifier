### 第一问现在跟哪一行

- `FulfillmentAssessment.expectation_id` + `status`

`spec/info-volume.md` 也是「细粒度 + 整体」两层，都还是第一问。

### 切粗会变成什么

把第二问做成案件级一列（「这个案子有没有这项功能」），对象就被切粗了。

I161 这类碰撞最清楚（不重判对错）：

| 第一问已经分开的件 | 若案件级只留一个第二问 | 丢掉的 |
|---|---|---|
| 「去年」/ 投保日 | 被投保人、全家保盖住 | 没立住的那一件消失 |
| 投保人 | 被收成「这个案子有功能」 | 立住了的那一件无法单独站 |
| 全家保 | 同上 | 同上 |

046 Consensus 已经说：I161 不得当「办成了 × 没立住」的合法证人，因为它更像第一问把「去年」盖掉了。
实现上若再做案件级第二问，就是用同一只手再盖一次。

`spec/alg/product-function.md` §3 还留着「按种类汇总整案」。039 / 040 已退休「认哪一类」。
本轮不改协议正文，但实现不得跟着旧 §3 去编案件级种类列。

### 切细会变成什么

为了更好答第二问，先把一件事拆成「姓名 / 年 / 天气」再查表，是 039 / 040 已死的操作化。

`required_capabilities` 看起来很像现成细项。它不是第二问。
`frontend_view.py` 把它原样摊在 Capabilities 列里，那是库存名，040 明确不看库存字段表。

同一条期望上若有多次 authority 调用、前缀不一致：不得为了得出更漂亮的「立住了 / 没立住」再把对象切开。读法见 058：说不清，差在哪儿 = 同一件上裁口不一致。

### 可证伪

1. 若案件级一列能保住 I161 里「去年」和「投保人」两件不同的产品事实，同时还不另立类型表，本 issue 不成立。
2. 若必须先把对象改写成更粗或更细的种类，第二问才能算，本 issue 和 040 冲突，应改送重开 040，而不是改粒。
3. 若 Capabilities 列已经是第二问，现行出口里应能不看这一次 Status 就读出立住了 / 没立住。现在读不到。

### 不是什么

- 不是重判 I161
- 不是给盘客 / 姓名 / 年 做题型

### Investigation

自己对了粒，不把「主表看不见」兑换成「所以对象要切粗」：

- 040 Consensus：对象仍是第一问那一件；不得另立类型表；不得为了更好答第二问把对象切粗或切细。合取（姓名且年）整件立住了没有，不得拆成两件再查表。
- 046 Consensus：I161 不得当「办成了 × 没立住」的合法证人；它更像第一问把「去年」盖掉了。
- `impl/core/schema/judge.py`：`BusinessExpectation.expectation_id`；`FulfillmentAssessment.expectation_id` + `status`。一行一件。
- `spec/info-volume.md`：细粒度 + 整体两层，值域相同，都还是 fulfillment，不引入 partial。整体是同一问的聚合语义。
- `impl/core/frontend_view.py` `_fulfillment_panel` L61–86：按 expectation 逐行拼矩阵，`status` 来自该行 assessment，`required_capabilities` 原样摊出。
- `impl/core/table_view.py` L107–109、L160–165、L277–301：行上 `status` / `fulfillment_status` 都来自 `overall_fulfillment.status`。案件表一行一个案子。
- `impl/frontend/summary.html` L107「状态」、L428–431 `renderCaseStatus`、L529 `fulfillmentStatus`、L377 三色 pill：吃的是整体第一问。
- `spec/alg/product-function.md` §3 仍写「认种类 / 一件事里有几类分开看 / 按种类汇总整案」。039 / 040 已退休「认哪一类」。本轮不改协议正文。

### Reasoning

这一条不是新发现的洞。现行出口已经按期望行切开第一问；040 已经禁止为了第二问改对象。本 issue 要锁的粒，就是现在这套粒。三个挑战都打不穿它。

**1. 主表「状态」看不见第二问，不是粒把兄妹藏起来了。**

用户现在只在案件表上看见「状态」，这是事实。那一格是 `overall_fulfillment.status`，一个词答整案第一问。059 说粒必须留在矩阵行上，意思是：**对象**跟哪一行走，不是**目光**现在停在哪一格。

兄妹不是被构造性删除。被禁止的是把第二问塞进这一枚芯片——那会同时切粗对象、一个词答两问。看见点是 060，看不看得见是 061。粒这一层只回答：就算以后要给人看，也不能把对象收到案件级类型列里再看。

**2. 整体第一问可以聚合，不是给整体第二问开类型列的许可证。**

`info-volume.md` 的整体 fulfillment 是同一问、同一三态、在细粒度算完之后的确定性上卷。它没有改对象，也没有另立「这个案子属于哪一类」。

案件级只留一个第二问（「这个案子有没有这项功能」）改的是对象。I161 这种碰撞最清楚：投保人 / 全家保 / 「去年」在第一问里已经是不同件；收成一个案件级词，没立住的那一件和立住了的那一件互相盖住。这不是 040 禁止的「类型表」四个字而已，是禁止切粗本身。

对称的、以后才谈得上的整体第二问，只能是：每条期望先有自己的第二问，再像 overall fulfillment 那样上卷。那是派生阅读，不能代替行，不能按 `product-function.md` §3 的种类去编。059 原文若被读成「永远不许有任何整体第二问」，过了。正确的锁是：没有案件级类型列，也没有「先切粗再答」的整体；有没有行之后的上卷，不是本 issue 要发明的，更不是现在的出口。

**3. 一条期望里混着已立住的检索和没立住的年份，不切开，不是把两件产品事实藏进这一行。**

040 合取针已经锁了：对象若在第一问里就是一件，第二问仍是整件。为了更好答第二问先拆成「姓名 / 年 / 天气」，是 039 / 040 已死的操作化。`required_capabilities` 看起来像现成细项，Capabilities 列不看 Status 也读不出立住了没有——它是库存名。

同一行上多次 authority 前缀不一致：058 的读法是说不清（同一件上裁口不一致），不是把对象切开。若「去年」其实是另一件用户要的事，那是第一问把对象写粗了（046 对 I161 的判断），先查第一问，不在第二问里补一把刀。

可证伪三条都立：案件级一列保不住 I161 里两件不同的产品事实；必须先改写成种类才能算，就该退回 040，而不是改粒；Capabilities 现在不是第二问。

本轮不加矩阵列，不重判 I161，不做盘客 / 姓名 / 年题型。
