# Issue #046: 产品功能不是 not_fulfilled 的附注

**Class**: boundary
**Severity**: high
**Status**: verifier-raised
**Evidence**: code-analysis
**Layer**: Protocol / 两问是否互相依存
**Cases**: 只作碰撞举例，不重判。

## Verifier Discovery

用户本轮的第一句：

> 我理解不是只有 not fulfilled 才有这个东西吗？

这句把第二问收成失败原因。本 issue 只钉：它是不是必须先看见「没办成」才能开口。

### 协议里两问谁也不当谁的前提

`spec/alg/fulfilled.md` §1：

> 我们：评测系统（Judge），只看一件事——系统有没有帮用户办成想办的事。

`spec/alg/product-function.md` §1：

> 本协议只看另一件事：用户要办的这类事，现在是不是这个产品已经有的功能？
>
> 任何一张表、一个标签、一句结论，都不能同时回答这两件。

同文件 §3 的判断顺序是：先认种类，再看在不在定位里，再看立没立住。三步里没有「先看 fulfilled」。

同文件 §2.3 硬前提 1：

> 不能因为「这次没办成」就说没这项功能，也不能因为「这次办成了」就说有这项功能。

若第二问只在 `not_fulfilled` 之后出现，这两句全部作废：没办成就被拿去证明没功能，办成了就根本不问。

### 权威消费已经写下「办成了 × 能力缺失」

`spec/alg/authority.md` §8.3：

```text
statement = 职责内能力缺失（应具备但未实现/表达不了）
    → 不强制改状态；Judge 结合 live 实际交付判断：
        期望未达成 → not_fulfilled
        实际达成   → fulfilled
```

「实际达成 → fulfilled」不是口误。它规定：能力缺失这一事实，不负责改写办成了没有。030 Consensus 已经据此改过「办成了不得自动排除正格」。

所以「只有 NF 才有」和现行 oracle 直接撞车。

### 只在 NF 后出现，会变成什么

| 做法 | 实际变成 | 踩哪条 |
|---|---|---|
| 只在没办成后问产品功能 | 失败原因 / 「尽力了」脚注 | fulfilled §2.2 不区分原因；product-function §6「尽力了不是状态」 |
| 办成了就默认有这项功能 | 用结果反推种类 | product-function §2.3 / §7.5 |
| 办成了就不再显示第二问 | F × 没这项功能 这格消失 | authority §8.3；product-function §6 左下格 |

`product-function.md` §6 的九格里，「办成了 × 没这项功能」写的是：

> 现有功能之外却被看成办成了。

这格不是装饰。它的工作是把「结果给到了」和「这类事已经立成功能」拆开。拆开之后才能看见：有人拿已经有的那类盖住没有的那类。

### 碰撞（形态，不重判）

| 例子 | 办成了没有 | 若只在 NF 后问 | 实际丢掉的 |
|---|---|---|---|
| 盘客名单没给 | 没办成 | 还能看见「盘客还不是现有功能」 | 无。这是用户直觉里最熟的一格 |
| 王坤林 | 没办成 | 会误读成「姓名查找还不是功能」 | 姓名查找已经立住；这里吵的是证据门槛 |
| 金凤 | 办成了 | 整列消失 | 现有功能里办成了，本应是对照里的多数格 |
| I161「去年」+ 投保人 / 全家保 | 新判定写成办成了 | 整列消失 | 投保日这一类还没立住；和 I046 同场景却看不见 |
| §8.3 明文：能力缺失但这次给到了 | 办成了 | 整列消失 | 协议已经允许的格子被显示层删掉 |

I161 本身可能是 fulfilled 口径虫（和 I046 打架）。就算它的 F 判错，也只能证明「这一案的第一问不稳」，不能证明「第一问一旦写成办成了，第二问就不该存在」。合法形态仍在 §8.3：能力缺失 + 实际达成 → fulfilled。

长尾 bad case 里，「没办成 × 没这项功能」会偏多。那是这批数据的分布，不是定义。换一批正常请求，「办成了 × 有这项功能」才是多数。第二问若只在失败后出现，正常分布上它会假装不存在。

### 可证伪

若存在一种读法，让第二问必须先看见 `not_fulfilled` 才能开口，同时还不违反：

1. product-function §2.3「不能因为这次办成了就说有这项功能」
2. authority §8.3「能力缺失 + 实际达成 → fulfilled」
3. fulfilled §2.2「没办成不区分原因」

则本 issue 不成立。

### 不是什么

- 不是说前端现在就要在办成了的案子旁边也画一列
- 不是重判 I161 / I046 / 盘客 / 王坤林
- 不是宣布「尽力了」是正式状态

### 未消元

- 办成了之后再写出「没这项功能」，算不算 Judge 改口：见 047
- 因此要不要给 fulfilled 加枚举：见 048

### Evidence Verification

协议原文支持「第二问不是 NF 的前提」。§3 判断顺序、§2.3、§10 都要求它能在不看 fulfilled 的情况下开口。§8.3 / fulfilled §3 / 030 明文留下「能力缺失 × 实际达成 → fulfilled」。

I161 **不能**当这格的合法实证。0814 投影自己写的是：投保人、产品两类办成了，拿它们盖住「去年」这类还没立住的事。这是 product-function §3 / §7.11 禁止的覆盖，更像第一问口径虫，不是 §8.3 的「同一期望实际达成」。verifier 把 I161 降成「形态例」是对的；原文里仍用它当「办成了整列消失就丢掉的东西」，过重。合法证人是协议格，不是这一案的 F。

前端现在只显示 fulfilled，只证明看见面，不证明第二问在定义上依附 NF。

### Reasoning

用户第一句把「这个东西」收成失败后才出现的附注。无论「这个东西」读成整条第二问，还是只读成「没这项功能」这一值，收成 NF 前提都会撞协议。

**1. 第二问的开口不看 fulfilled。**

product-function §3 的输入是「用户要办的是哪类事」，不是 `status`。§10 把「不需要先看 fulfilled」写成验收。先看见 `not_fulfilled` 才准问，等于改验收。

**2. 只在 NF 后出现，会把第二问收成原因。**

fulfilled §2.2 已经规定：没办成不区分原因，「功能本身未实现」仍是没办成，不是另一种状态。product-function §2.3 禁止「这次没办成 ⇒ 没这项功能」。NF 门控正好做这两件：用失败给第二问发通行证，再用第二问给失败分类。盘客那一格读起来最顺，是因为长尾分布里它常见，不是因为它是定义。

**3. 「办成了就默认有功能 / 不再问」直接废掉 §2.3 后半句。**

金凤那一类是「办成了 × 有这项功能」。这不是装饰，是正常请求上的多数格。第二问若只在失败后出现，成功案上它靠沉默装成「有这项功能」。这正是 §2.3 / §7.5 禁止的反推。

**4. 攻击成立一半：I161 不是合法 F × 没这项功能；§8.3 也不是「别的种类办成了，把缺的那种继续挂着」。**

§8.3「实际达成」接的是 fulfilled §3 第三步：看**这一条期望** live 有没有给到。Authority §8.2 已经声明它不评「本次输出是否达标」。所以合法组合是：

```text
Authority：这类办法当前缺（职责内能力缺失）
Judge：    这一条期望这次给到了 → fulfilled
```

这是「办法仍缺，这次绕过 / 碰巧给到」，030 已锁为正格。它不是：

```text
投保人 / 产品给到了
去年没给到
整体写成办成了
再用第二问把「去年」留在画面上
```

后一种是第一问覆盖，不是第二问的生存证明。若每一个「F × 没这项功能」都只是 Judge 判错，**「没这项功能」这个值**在正确判定里会大量落在 NF 上——这是分布，不是定义。正确判定下，第二问在 F 上仍要开口，多数答「有这项功能」，少数合法格仍是「同一期望实际达成」。它不会塌成「正确判定下只剩 NF 脚注」。

**5. 本 issue 不批准看见面。**

「办成了旁边也要画一列」是章程 §4，不是 046 的锁。046 只锁：定义上不得先看 NF 才准问。

可证伪三条仍立。不存在一种读法，能让第二问必须先看见 `not_fulfilled`，同时还不踩 §2.3、§8.3、§2.2。I161 被拿掉之后，这三条仍然立。
