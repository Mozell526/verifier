## 目标

以调用方视角，从算法 API 入口逐个验证高层能力，挖掘潜藏的效果缺陷并修复。
范围：高层算法 API（检索增强、总结、多轮对话、工具调用等），不含底层 LLM 中转。

# 什么是 bug

不同于功能崩溃，算法 bug 是"看起来正常、实际劣化"的静默问题，按三个维度定义：

- 信息量充分性：该进上下文的关键信息缺失、被截断、多轮后被遗忘或被污染
- 有效信息密度：上下文塞满无效冗余，关键信息被淹没
- 模型效果：幻觉、违反关键约束、分支/工具选错、输出格式不合规

## 如何挖掘

从常规用例想不到的角度构造输入：

- 边界输入：空、超长、重复、矛盾、中英混排、特殊字符、注入
- 交叉场景：多轮上下文累积、多文档联合引用、多能力组合调用
- 观察手段：从日志抓取实际组装的 prompt 与 token 用量，核对信息量与密度是否合理；同一输入多次采样，看结果稳定性

## 如何探索

阅读代码 + 构造用例，全部从 API 正常入口验证。

允许：查日志（实际 prompt、token 用量）、查数据库记录、构造任意正常入口可达的输入。

不允许：直接调用底层 LLM、手动篡改送入模型的上下文来构造场景。所有缺陷必须能通过高层 API 的正常调用复现。

## 修复方式
发现即修，用相同输入路径回归验证。bugs.md 记录发现与修复过程。

每个 bug 打修复方案确定性分；< 80% 不修，移入 open-bugs.md，只记复现路径、预期结果、实际结果。无论修不修都记分。

## 停止条件

- 时间超过 10 小时
- 或完成一轮计划内的探索并修复所有 bug
