# 知识查证需求

> 状态：已确认（2026-10-14）。确认后再写方案（`spec/alg/knowledge-evidence.md`）与实施记录（`spec/implementation/knowledge-evidence.md`）。

## 1. 要解决什么问题

被测系统的回答里有大量具体事实（期限、金额、比例、条件、某产品有没有某项责任）。评测要知道这些事实有没有依据，就得**去被测系统用的知识源里查**。

现状（真实性轴）是固定流程：抽出回答里的事实 → 每条事实开一个检索小循环 → 判支持 / 矛盾 / 查不到。实测下来有三个问题：

1. **查法写死在流程里。** 不同场景的查法差异很大：有的按产品名 + 条款事项查，有的要先查客户再查保单（多跳），有的知识源只有业务系统自己的查询接口（MCP）。固定步骤覆盖不全，每多一种场景就要改流程。
2. **"查"和"判"混在一起。** 查到了什么、没查到什么，跟最后怎么判，挤在同一步里，出了问题分不清是没查到还是判错了；查到的东西也只有真实性轴自己能用。
3. **接新知识源要改评测器。** 每多一种知识源类型（ES、MCP、以后的关系库……），都要在评测器里写连接、检索、回读。我们希望以后接新知识源只改那个知识源自己的 MCP 服务，评测器不动。

## 2. 我们要什么

### 2.1 一个独立的「知识查证」轴

新增一个扩展轴，只做一件事：**针对被测回答里的事实，到场景声明的知识源里取证，交出一份「知识案卷」。**

- 它**只取证，不判对错**。判定由下游轴做。
- 它与过程六轴前面的「过程案卷」是同一类东西：过程案卷从业务 trace 取证，知识查证从知识源取证。

### 2.2 查证由模型自主进行

怎么查（查什么词、先查哪个知识源、要不要多跳、什么时候够了）由模型在工具循环里自己决定，用项目已有的 ToolLoop。理由：查法随场景千差万别，用固定流程覆盖不好，需要模型发挥主观能动性。

但下面这些不交给模型，由程序保证：

- **查哪些知识源**：只能用场景声明并登记过的知识源，别的查不了。
- **什么时候算查完**：模型不再调用工具只是申请结束；必须交出的案卷通过程序验收，才算结束。
- **证据可信**：见 2.5。

### 2.3 待查清单

- **清单由单独的抽取步骤先给出**，查证开始前就定好；查证只负责查，不负责定"查什么"。理由：同一个模型既定清单又查，会倾向少列难查的事实，且程序无从发现。（2026-10-14 已定）
- **抽取方式可替换**：查证只认"出清单"这一接口，里面现在是一次独立的模型抽取（沿用现有抽断言：逐字摘自回答、带具体值），以后可换成更好的抽法甚至子循环，查证部分不动。
- **清单可追加、不可删除**：第一版不提供查证中补充条目的手段，但结构上留出追加的位置；是否加，看验收中漏抽的实际分布再定（见 §4）。
- **清单来源可扩展，每条标明来源轴**：所有需要知识依据的轴都可以往清单里提自己的待查项，查证一次查完，各轴读自己那几条（也可读别的轴的）。第一版只有真实性一路。（2026-10-14 定）
- **待查项分两种**：
  - **核对说法**：回答里说出的事实（"实际"那一侧），问"知识库怎么说这件事"。第一版只做这种。
  - **查问题**：针对用户问题，问"知识库对此有哪些规定（含条件、限制、例外）"（"本应"那一侧）。只列问题，不列答案；由谁判"漏没漏、漏的算不算错"见 §5 ⟡6。
- 查证循环不自己往清单里加"本应说什么"：定"查什么"是清单来源的事，判"漏没漏"是判定轴的事，查证只取证。
- 查一条事实需要的中间信息（如先查产品代码、保单号）不进清单，是查证过程本身。

### 2.4 案卷要交代清楚每一条待查事实

所有待查事实在一次查证里一起查（知识源的返回可以共用），但**逐条提交、逐条验收**，以免 A 的证据串给 B。（2026-10-14 已定）

案卷对每一条待查事实，都要给出两种结果之一，并附上检索记录（查了哪个知识源、用了什么查询、拿回了什么）。原文与事实是支持还是矛盾，由下游判定（2026-10-14 定，见 §2.6）：

| 结果 | 含义 |
|---|---|
| 找到相关原文 | 知识源里有讲同一对象、同一事项的原文（附逐字引用） |
| 没找到 | 查过了，知识源里没有相关原文 |

- **不能漏**：每一条待查事实都必须有结果。漏一条，案卷不收。
- **没找到必须真查过**：对这条事实一次都没查，就交"没找到"，不收。已经实际遇到过：模型一个工具都没调，就说"查不到"。
- **归属要对**：原文必须属于同一个对象、同一个条件。别的产品的同类条款不能拿来支持或反驳。
- **正反都查**：每条都要同时找支持的、矛盾的、附加条件或例外（如"经社保结算"、其他版本、免责），不能找到一段支持的就停。查的人可以有自己的判断来决定往哪查，但判断不写进案卷。
- **相关原文全部引用，不挑**：找到的相关原文都要交，包括互相矛盾的（如 70% / 80% 并存时两段都引）。挑过的证据会把下游判定带偏。

### 2.5 证据必须可回查

- 案卷里引用的每一段原文，都必须出自**本次查证中实际调用工具拿回的返回**，并能由程序逐字核对。模型转述、改写、凭记忆写的，都不算证据。
- 检索记录完整保存，事后能看到"查了什么、看到了什么、据此交了什么"。

### 2.6 下游复用

- **第一个消费者是真实性轴**：改为读案卷，看引用原文判支持 / 矛盾 / 查不到，判定本身仍是固定流程，不再自己调工具。
- 之后承载性轴、能力兑现轴需要知识依据时，提自己的待查项（§2.3），读同一份案卷，不各自再查一遍。
- 现有口径不变：说错的判没办成；查不到的判无法评估（2026-10-14 已定）。

### 2.7 接新知识源只改 MCP，不改评测器

- 评测器对知识源只认一种接口：MCP 工具（工具名、说明、入参取自 MCP 服务自己的声明）。
- 接一个新知识源 = 写好或配好它的 MCP 服务，再到资料管理页「知识源」登记；评测器代码不改。
- 已有的 ES 与资料库也要逐步走同一接口（⟡ 节奏见 §5）。

对 MCP 服务的要求：

- **只读**：登记时声明允许评测使用哪些工具；有副作用（会改业务数据、会办理业务）的不放开。带身份的查询工具照常放开，工具需要什么参数就给什么（2026-10-14 定）。
- **返回带原文**：能被引用的东西必须以原文出现在工具返回里；只回答"是/否"的工具不能作为证据来源。

### 2.8 资源有边界

- 每次查证有上限（模型轮数、工具调用次数、时长），超了这个轴记为**执行失败**，不能悄悄变成"没找到"。否则下游会据此判"无法评估"，等于让预算决定结论。
- 工具返回可能很大（实测一次 6.4 万字），不能整段反复塞给模型；完整原文由程序保存，模型按需翻看。

## 3. 不做什么

- 不判对错。判定留给真实性等下游轴。
- 不改主判（生产 judge），不改过程六轴；主判是否改用工具循环，以后逐步尝试，不在本需求内。
- 不处理被测系统返回 200 但响应体带错误码、或返回降级文案的情况（2026-10-14 定：先不管）。
- 不接关系库（以后再说）。
- 不替业务裁定知识库内部的矛盾：知识库对同一问题有互相矛盾的口径时（实测：可贷比例 70% / 80% 并存），如实记下两边原文，不判哪条对。

## 4. 验收

对照现在的真实性实现，用同一批样本（本次实验的 F01–F10、L01–L05、M1–M3，标准答案已人工核定），另补几条真实的长回答样本（多段、带列表的保险回答，人工标出应抽出的事实）——现有样本每条只有 1–4 个短事实，测不出漏抽：

| 项 | 要求 |
|---|---|
| 判定正确率（经下游真实性轴） | 不低于现状 |
| 轴执行失败率 | 不高于现状 |
| 漏查（待查事实没有结果） | 0 |
| 漏抽率（人工标注的事实没进清单） | 如实报数；漏掉的逐条归类：①抽取口径排除（如不带具体值的"逐年递增"）②看了知识库才知道能核对 ③长回答/列表里抽漏。①③多则调抽取，②多则加查证中补充条目 |
| 引用回读通过率 | 100%（不通过的不进案卷） |
| 没查就交"没找到" | 0 |
| 耗时、模型调用次数、工具调用次数 | 如实报数，与现状对比；不设硬门槛，但大幅变差需要说明 |
| 接新知识源只改 MCP | 演示一次：新登记一个 MCP 知识源并在场景中引用，评测器代码零改动即可查证 |

## 5. 待定 ⟡

1. ~~待查清单什么时候定~~ → 已定，见 §2.3。
2. ~~一次查全部还是逐条查~~ → 已定，见 §2.4。
3. ⟡ **ES 与资料库何时改走 MCP。** 知识查证轴跑通并完成对照验收后，**优先做这一条**（2026-10-14 定）。
4. ⟡（暂缓，目前无影响）**有业务 trace 的场景是否也启用。** 业务 trace 里已有业务系统自己检索到的内容，可以与知识查证的结果对照（业务查到了但没用上 / 业务根本没查到 / 知识库里就没有）。价值大，但涉及过程轴，另一进程在改，建议放到后面。
5. ⟡（暂缓，目前无影响）**案卷是否直接给能力兑现轴读。** 现在能力兑现通过真实性的结果间接使用；直接读案卷能做更多（例如按知识库推出"本应答什么"），但会改能力兑现，而主轴还在调。
6. ⟡（排在 ⟡3 之后）**核心要点漏说。** 漏说核心要点很多时候也属于说错（2026-10-14 用户指出），现在是盲区：真实性只核对说出来的话；能力兑现只看人写的期望，知识库里有、但没写进期望的核心要点没有轴能发现。（说了值但漏了条件，如 F08"报销比例百分之一百"漏"经社保结算"，现在已由真实性判 refuted，不在此列。）做法：清单加"查问题"项（第一版每个用户问题一条，程序生成），查证取回相关原文，由判定轴对照回答判漏没漏、算不算错。判定放哪个轴待定，倾向能力兑现（"是不是核心"取决于用户要办成什么）。
