> 状态：打磨中（2026-10-05 起）。这份文档是过程六轴后续所有抽象、枚举、实现的依据；先把需求写准，再谈方案。

## 1. 我们要什么

被测业务系统跑一个 case，会留下一条业务 trace。过程六轴读这条 trace，对业务系统的六项过程能力各给一个结论：

- 意图理解、规划路由、工具执行、知识数据、模型能力、上下文管理。

每个 case、每个轴，产出两样东西：

- **verdict**：枚举值，表示被测系统在这个轴对应的能力上，本次表现如何。它像一个评分，要能跨样本汇总。
- **reason**：这个轴看到的具体问题，每个问题要有 trace 里的依据。

六轴不是最终目的。拿到各 case 的六轴结果之后，要能从下面四个角度得到东西。四个角度是需求的主体，后面的方案都对着它们验收。

## 2. 四个使用角度

### 2.1 看整体：业务系统的各项能力哪些好、哪些差

对一个样本集汇总六轴 verdict，看出被测系统的上下文工程能力、意图识别能力等等各自处于什么水平。然后对差的轴，直接下钻看它在业务系统里具体哪些地方做得不好，形成一份对业务方有意义的反馈。

这要求：

- verdict 的含义要稳定、跨 case 可比，同一个值在不同 case 里说的是同一件事；
- verdict 说的是**这项能力**。上游造成的结果不好，不能算到这个轴的能力头上，否则汇总出来的"能力水平"是错的；
- 从轴的汇总能一路下钻到具体 case 的具体问题。

### 2.2 看单个 case：具体出了什么问题，依据是什么

打开一个 case，能直接看到有哪些具体问题，每个问题指向业务 trace 里的原文。这是我们需要业务 trace 的地方。

这要求：

- 问题要具体到"哪一步、什么现象、预期是什么、实际是什么"，不能只说"某模块有问题"（同 `demand/agent.md` 归因要求）；
- 每个问题带可回查的 trace 引用；
- 该做而没做的事（例如本该查询却没发查询）也要作为问题记下来，不能因为 trace 里没有这一步就看不见它。

### 2.3 看聚合：把各 case 的问题聚类

case 多、轴多，必须能把问题聚合起来看。现在已有聚类页。聚类做得好的前提是前面两步的产物本身是干净的：问题是独立的、结构化的、带依据的。

这要求：

- 聚类的成员应当是**一个个问题**，不是整段轴级 reason。一条轴级 reason 里常常装着多个不同的问题；
- 同一个问题在不同 case 里要能被认出来是同一类。

### 2.4 看评测系统自己：确保上面三条做得对

六轴判得不准，上面三条全是错的。所以需要能看评测系统自身的运行记录，确认它的判断有依据、稳定、没有把评测器自己的失败伪装成业务问题。为此有了针对 verifier 自身的 llmtracing 模块（注意：这是评 verifier 自己的，不是读业务系统的 llmtracing provider）。

这要求：

- 评测器运行失败（模型没给出合法输出、超时、预算耗尽）必须和"业务证据不足"分开记录，不能混成一个 not_evaluable；
- 每条 verdict 和每个问题都能追到评测器当时看了什么材料、依据什么判的。

⟡ tool-loop 方案是为效果和成本可控做的尝试，是否必要还没定，暂缓，不在本文范围内约束。

## 3. 现在已经碰到的具体问题

这些是需求必须覆盖的实际案例，后面方案拿它们验收。

| # | 现象 | 为什么现在分不清 |
|---|---|---|
| P1 | 知识轴：A）上游根本没发查询，所以数据没拿到；B）查了，数据源确实没有应有的数据 | 两种都判 fail / problematic，看不出 A 不是数据源的问题。两种都要记，但给出的结论不能一样 |
| P2 | 工具返回为空，看不清是工具丢了条件还是数据源没有 | 现在两轴都 problematic 并写"原因未定位"，但只在自由文本里 |
| P3 | 模型输入里关键提示被系统丢了，模型的回答因此不对 | 模型轴判 sound 并在文字里注明"受上下文影响"，这个事实下游看不到 |
| P4 | 一个轴里既有已判出的问题，又有判不了的项 | 轴级只剩一个 problematic，判不了的那部分被盖掉 |
| P5 | 一个轴全部 pass，但有义务缺判准 | 轴级 sound，容易被读成"全部核实正常" |
| P6 | 评测器输出不合法被补成 insufficient_evidence | 和真正的业务证据不足混在一起 |
| P7 | 聚类输入是整段轴 reason | 一条 reason 含多个独立问题，聚类分不开 |

P1 不是知识轴独有。意图理解（历史没传所以指代解析不了）、规划路由（意图漏了子问题所以没安排工作）、模型能力（P3）都有同样的结构：结果不对，但原因在上游。需求是对这种情况有**一条统一的处理口径**，而不是每个轴各写一套。

| 事项 | 结论 | 定于 |

| verdict 的含义 | 这个轴对应的被测系统能力本次如何。有问题的话在 reason 里指出 | 2026-10-05 |
| 问题从哪来 | 两条都要：从运行里发现的偏差（分析轴召回）；从期望和系统设计倒推"该发生什么"再去运行里核对（发现该做没做） | 2026-10-05 |
| verdict 枚举体系 | "每轴一个 verdict 枚举值 + reason"这个体系是 verifier 整体框架在用的，不另起一套。但过程六轴当前用的四个值 `sound / problematic / not_evaluable / not_applicable` 不是定死的，见 §5 | 2026-10-05 |
| 判定单位 | 子能力 × 这个子能力的一次行使。子能力从部件的"输入 → 输出"推出，不手列 | 2026-10-05 |

| verdict 取值 | 五值：problematic / not_evaluable / sound / untested / not_applicable。untested = 本应行使但没有一次输入有效的行使，本次对这项能力没有结论。verdict 必带组成 | 2026-10-05 |
| 归因未定位（P2） | 两轴 not_evaluable，问题记录归因写"未定位{轴, 轴}"。不变量改为"结果坏 ⇒ 问题列表至少一条" | 2026-10-05 |

## 5. 还没定的 ⟡

- ⟡ 主轴（扩展轴 fulfilled）怎么基于六轴综合判断。方向已定（§4），具体规则和启用时机未定。
- ⟡ "问题"的结构化字段最少要哪几个。目前看至少要：现象、trace 引用、归到哪个轴、对最终结果有无影响。方案 `spec/alg/process-axes.md` §4 给了一版，待实际样本验证。
- ⟡ 六个轴本身是不是最合适的划分，不锁死；但目前以这六个为准推进。

## 6. 不要什么

- 不要为了区分 P1 给每个轴硬加一串故障类型枚举，分不出"为什么是这几个"的枚举没有信息量。
- 不要用 verdict 一个值同时表达"能力如何"和"结果如何"。
- 不要让评测器自己的失败变成业务结论。
- 不要为了让汇总好看而改口径（例如把该判的问题改成不适用）。

## 7. 验收怎么看

- 第 3 节的 P1–P7 每一条，在新方案下给出的输出要能让人一眼区分开，并且说得出为什么这样分。
- 用已冻结的样本（`report/` 下的快照与 A–E 校准轨迹）做对照：旧输出 vs 新输出并排，由人核对是否准确表达了业务含义；不以通过率为目标。
- 2.1–2.3 三个角度各走一遍：能从轴汇总下钻到 case 问题，能从 case 问题回到 trace 原文，能把问题而不是整段 reason 送进聚类。
