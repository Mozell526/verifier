# 信息源需求

> 状态：打磨中（2026-10-17 起）。本文定义评测过程中取用的**信息源**是什么、有哪几种、各自能说明什么、要满足什么要求。它是 trace 取证、知识查证、业务描述等后续方案的依据。
> 方案类文档（`demand/business_trace_langfuse.md`、`demand/knowledge_evidence.md`、`spec/alg/material-positioning.md` 及各 provider / 知识源的实现文档）与本文冲突时，以本文为准，回来修方案。
> 标 ⟡ 的条目还没定，需要讨论。

## 1. 信息源是什么

评测一个 case，流程上有五个位置：

```text
① 输入端        用户原话、历史、下游要求、场景判准   ──→  目标（demand/expectations.md）
② 被测系统运行  产出回答，同时留下 trace
③ 信息源        评测方在判定过程中取来用的信息         ←  本文
④ 判定          结论：主轴三态、过程六轴 verdict        （spec/alg/fulfilled.md、demand/process_axes.md）
⑤ 归因          优化建议
```

信息源是 ③：**既不是输入，也不是结论，是评测方在判定时取用的东西。**

开放文字类场景（回答是自由文本，里面有大量具体事实、条件、流程），光看问答文本判不了对错、也判不了过程哪里出了问题。评测方必须有信息源。现在在补的 trace 能力和知识能力，就是 ③ 里最重要的两种。

### 1.1 有哪几种

按两个维度摆：谁产生的（被测系统自己 / 被测系统之外），什么时候有（每个 case 动态产生 / 项目级静态登记）。

| | 被测系统自己产生的 | 被测系统之外的 |
|---|---|---|
| **case 级、动态** | **trace**：这一轮运行留下的记录 | **知识**：评测方到知识源查到的 |
| **项目级、静态** | 系统静态资料：代码、配置、能力声明 | **业务描述**：业务方登记的事实；**参考答案**：人工或业务方给的标注 |

trace 和知识是重点。另外两格是配角，但要有位置，否则它们会被当成 trace 或知识混用。

横轴的意义：被测系统自己产生的东西，只能说明"系统做了什么、怎么做的"，**不能证明系统做得对**。系统自己的输出证明不了自己。独立于系统的东西才能证明对错。静态那一行的细分见 `spec/alg/material-positioning.md`，本文不重复。

### 1.2 每种信息源

| 信息源 | 谁提供 | 能说明什么 | 不能说明什么 |
|---|---|---|---|
| **trace** | 被测系统运行时留下，评测方通过 provider 取回（agno、langfuse、llmtracing） | 业务这一轮做了什么：查没查、拿到什么返回、把什么交给了模型、模型输出了什么、有没有核实 | 业务说的对不对 |
| **知识** | 评测方自己到场景登记的知识源查（MCP、ES、资料库） | 回答里的事实在知识源里有没有依据：有原文支持、原文矛盾、查不到 | 业务有没有去查、过程可不可靠 |
| **业务描述** | 业务方登记（场景框引用的资料、知识源登记说明） | 怎么读别的信息源：系统是干什么的、对象靠什么区分（如产品按险种代码）、数据单位、各源返回怎么读（如"本页条数等于总数即全量"） | 不是结论的依据，只是读法 |
| **参考答案** | 人工核定或业务方确认的标注 | 对照用 | AI 生成的伪参考不构成依据（material-positioning §5.4） |
| **系统静态资料** | 被测系统的代码、配置、能力声明 | 系统设计上怎么做的；开放场景常拿不到，trace 是它的动态替身 | 同 trace，证明不了对 |

被测系统运行时自己说的话（system prompt、能力提示、自带 guardrail / evaluator 的输出）不单列，它们就在 trace 里，按"系统自己说的"对待。

### 1.3 信息源在流程里的身份

同一个信息源在 ④ 里会以不同身份被用到。本文只列身份，怎么用是判定的事。

| 身份 | 做什么 | 例 |
|---|---|---|
| **依据** | 被某条结论引用 | "没办成"指向 trace 里某次调用的返回 |
| **读法** | 帮着读别的信息源 | 业务描述告诉判定"两个代码不同就是两款产品" |
| **对照物** | 两个来源互相比 | 业务 trace 里查到的 vs 评测方在知识源查到的 |
| **缺口信号** | 它不在，本身就是信息 | 没埋点、脱敏、没登记知识源 → 下游知道缺的是哪一格 |

## 2. 信息源不是什么

- **不是输入。** 用户原话、历史、下游要求归 ①，由 `demand/expectations.md` 管。多轮里用户下一句话能反映上一轮办没办成，那是 ① 的信息被 ④ 用了一下，不改变它的位置。
- **不是结论。** 三态、verdict、每条事实的支持/矛盾都是 ④ 产出的。
- **不是评判标准。** 本文不定义任何结论怎么判。判别法：一句话写进本文之前问一句，**把判定模型换掉、判法全部重写，这句话还成立吗？**成立才是本文的内容。
  - "trace 证明不了业务说的对不对" → 成立 → 本文。
  - "缺证据判说不清" → 是判法 → `spec/alg/fulfilled.md`。但"缺口必须能被下游看见、能说出缺哪一格" → 成立 → 本文。
  - "没查就不能报没找到" → 是取证过程的完整性要求，不是判法 → 本文。

本文保证"缺了什么"这个信息存在；缺了怎么判，归判定文档。

## 3. 谁用信息源

| 用的人 / 环节 | 用哪些 | 拿来干什么 |
|---|---|---|
| 主轴（办成了没） | trace、知识、业务描述 | 结果有没有证据；没有的话缺哪一格 |
| 过程六轴 | trace、业务描述 | 每一环做了什么、本应做什么（`demand/process_axes.md` §2.2） |
| 真实性 / 知识查证 | 知识、业务描述 | 回答里每条事实有没有依据 |
| 业务开发 | 全部，经由 ④ 的引用 | 看到问题时能回查到原文：哪一步、哪句话、原文是什么 |
| 评测方自己 | 全部 + 评测器运行记录 | 确认每条结论依据什么判的、信息源采到什么程度（`demand/process_axes.md` §2.4） |

两个来源**对照**是开放场景里最有价值的用法：业务查到了没用上 / 业务没查、知识源里有 / 知识源里就没有。这要求同一件事在 trace 和知识两边都取得到。对照出来的结果意味着什么，归判定。

## 4. 信息源要满足的要求

1. **取得到。** 每个 case 都能取到场景声明的信息源；取不到要有明确记录，不能静默跳过。
2. **关联精确。** 这条 trace 必须就是这一轮：用业务自己的 ID 对上唯一一条，查到零条或多条都算失败，不按时间、会话、正文去猜。
3. **只读。** 知识源的工具只放开只读的；有副作用的不放开。带身份的查询工具照常放开，工具需要什么参数就给什么。
4. **完整性可见。** 采到多少、缺哪段、哪里脱敏、哪里截断、哪些调用没埋点，都标出来，传到下游。缺证不能悄悄变成通过，也不能悄悄变成失败。
5. **原文可回查。** 信息源要以程序能逐字回读的形式保存：取回什么就存什么，不转述、不改写。这样 ④ 引用它时才核对得了；引用时必须回读是判定文档的要求，不在本文。
6. **真查过才能说没找到。** 对一条事实一次都没查，不能报"没找到"。查证过程本身要有记录。
7. **评测器自己的失败和缺证分开。** 超时、预算耗尽、输出不合法是评测器失败，不是业务证据不足，两者不能混成一个说不清。
8. **改被测系统只为关联。** 为了让评测方找到"这一轮是哪条 trace"，可以让业务传一个 ID；此外不为取证改业务、不补埋点。缺口写进报告，由业务方决定补不补。
9. **业务描述只写数据事实，不写判法。** 单位、对象标识、别名对应、返回怎么读，可以写；"回答写了单位就算对""名字像就算同一款"不能写。怎么判是评测系统的事。
10. **业务事实不进评测系统。** 评测系统里不内置任何具体业务的事实（某系统金额单位是元、某系统产品按险种代码认）。这些由业务方写进业务描述，评测系统照着读。

## 5. 现在已经碰到的具体问题

这些是需求必须覆盖的实际案例，后面方案拿它们验收。

| # | 现象 | 属于哪一格 / 哪条要求 |
|---|---|---|
| S1 | 业务搜索工具内部四步（解析问话、整理、查库、整理返回），trace 里只记了外层入参出参，中间两步只有字节数和状态码；看不到实际按什么条件查的 | trace；要求 4（缺口要可见）、要求 8（不补埋点，写进报告） |
| S2 | Langfuse 上报默认脱敏（保单号、手机、姓名换成 `[REDACTED]`）并截断到 4000 字，截断不留标记；实测 12 次模型输入全部超长，最先被截掉的是本轮问题和工具结果 | trace；要求 4（长度正好等于上限的一律标 truncated） |
| S3 | 评测方没有连接客户数据源，业务回答"客户号 X 对应某人"对不对核实不了 | 知识；缺口信号——缺的是知识那一格 |
| S4 | 查证模型只读了长返回的开头一小段，后面的关键字段没看到就说"没找到"（伏云平"产品总保额 750,000"连错 3 轮） | 知识；要求 6（真查过）、要求 5 |
| S5 | 模型一个工具都没调，直接说"查不到" | 知识；要求 6 |
| S6 | 业务产品查询对问法敏感：搜"安佑福"返回的都是别的产品，只有特定问法才返回代码 1836 的那款；查证拿了名字相像的另一款（1813）当证据 | 知识；要求 5 的归属（原文必须属于同一对象），以及业务描述该写清"产品按险种代码区分" |
| S7 | 业务数据里金额不带单位，有的字段写明"单位未说明"；回答写了"元"，判定拿不准 | 业务描述；要求 10（事实没地方放，就会被塞进评测系统） |
| S8 | 读法说明里混进了判法和查法类的话（"hint 里混着表述要求，不是数据""可以再按保单号逐个查详情"），一句被判定当成了冲突依据，一句让查证多查了三成 | 业务描述；要求 9 |
| S9 | 知识源登记时写死了一个工号，业务按 case 的工号查；身份应来自样本请求 | 知识；要求 3（工具需要什么就传什么） |
| S10 | 工具一次返回 6.4 万字，不能整段反复塞给模型 | 知识；完整原文由程序保存，模型按需翻看 |
| S11 | Langfuse 写入是异步的，刚跑完就取可能缺步骤；业务开了采样时本轮可能有调用不在 trace 里 | trace；要求 1、4 |
| S12 | 评测器超时 / 预算耗尽后，下游拿到的是"无法评估"，分不清是业务证据不足还是评测器没跑完 | 要求 7 |

## 6. 已经定下的

| 事项 | 结论 | 定于 |
|---|---|---|
| 评测器失败与证据不足分开记 | 两者不能混成一个 not_evaluable | 2026-10-05（process_axes §2.4） |
| 知识源只读、白名单 | 登记时声明允许评测使用的工具；有副作用的不放开；带身份的查询工具照常放开，工具需要什么参数就给什么 | 2026-10-14 |
| 没查就报没找到不收 | 对一条事实一次都没查，交"没找到"不收 | 2026-10-14 |
| 知识源内部矛盾不裁 | 知识库对同一问题有互相矛盾的口径时，两边原文都记，不判哪条对 | 2026-10-14 |
| 业务 trace 缺证明确降级 | 业务已有的埋点能给多少证据就用多少，缺的明确标出来 | 2026-10-15 |
| 改被测系统只为关联 | 只传一个让评测方找到本轮 trace 的 ID；不为取证补埋点；缺口写进报告由业务方决定 | 2026-10-16 |
| 取证能力列入总需求 | `demand/demand.md` 第 7 条：trace 和知识查证两种取证能力；开放场景通常需要其中一种或两种；用不用、用哪种由场景声明 | 2026-10-16 |
| 业务事实不进评测系统 | 单位、对象标识这类事实由业务方写进业务描述，评测系统照着读；没写的，对不上就是对不上 | 2026-10-17 |
| 业务描述只写数据事实 | 不写判法、不写查法 | 2026-10-17 |
| 信息源的范围 | 只管 ③：取得、性质、完整性；不管怎么判 | 2026-10-17 |

## 7. 还没定的 ⟡

- ⟡ **场景怎么声明自己需要哪些信息源。** 闭合场景（输出直接能对）不需要 trace 和知识；开放场景需要一种或两种。现在没有声明的位置，也没有"声明了但没取到"和"本来就不需要"的区分。
- ⟡ **trace 缺证分几级。** 全采到 / 部分采到 / 脱敏 / 截断 / 没埋点 / 采样丢失，各级怎么标、下游怎么看见。langfuse 需求里有"部分采到"的雏形，没统一。
- ⟡ **业务描述写在哪、谁维护。** 现有两个位置：场景框引用的资料（`{material://}`）、知识源登记的说明。倾向：业务层面的事实进资料，某个源的返回怎么读进该源的登记说明。接 `demand/expectations.md` §7 两条 ⟡。
- ⟡ **知识源身份从哪来。** 登记写死工号，还是从样本请求取（如 `${request.body.empno}`）。倾向后者，这会改知识源登记协议。
- ⟡ **参考答案的站位。** 人工核定的标签能不能作为 ④ 的依据，还是只用于评测自检。目前只用于自检。
- ⟡ **trace 与知识对照什么时候启用。** `knowledge_evidence.md` ⟡4 标为暂缓。本文认为它是开放场景里最有价值的用法，建议提前。
- ⟡ **用户后续反应。** 多轮里用户下一句能反映上一轮办没办成，归 ① 还是也算 ③ 的一种。倾向归 ①，本文只引用。

## 8. 不要什么

- 不为取证改被测系统（关联 ID 除外）。
- 不把业务事实写进评测系统。
- 不把系统自己的输出、配置、能力声明当作"系统做得对"的证明。
- 不让缺证悄悄变成通过，也不让它悄悄变成失败。
- 不让预算、超时、模型没跑完变成"没找到"。
- 不在业务描述、读法说明里写判法。
- 本文不写任何"怎么判"。

## 9. 验收怎么看

- 每个 case 能列出：用了哪些信息源、各自采到什么程度、缺哪一格、缺在哪一步。
- 信息源里的任何一段都能由程序按位置回读到原始记录；取回的内容和保存的内容逐字一致。
- 缺证的 case，下游输出里能看见缺的是哪一格，而不是一个笼统的"无法评估"。
- 评测器自己失败的 case，和缺证的 case，在输出里分得开。
- 新接一个 trace provider 或一个知识源，不改 ④ 的判定代码。
- "没查就报没找到"为 0。
- §5 的 S1–S12 每条都能在方案里找到归属和处理方式。
